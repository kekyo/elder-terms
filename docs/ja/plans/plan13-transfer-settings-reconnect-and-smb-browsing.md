## 目的と合意事項

ファイル転送の設定ダイアログへ接続の色を適用し、自動クローズを無効にした場合は、全接続方式で切断後に再接続できるようにします。SMBではサーバーが公開する共有の一覧をツリーのルートに表示し、ユーザーがそこから各共有を探索できるようにします。

利用者から報告された問題は、転送設定のダイアログに接続の色が反映されないことと、SSH切断時のオーバーレイに再接続ボタンが表示されないことです。再接続ボタンはSSHに限らず、ほかの種類の接続にも表示する方針で合意しています。

SMBの共有ブラウズでは共有名の設定項目を削除し、リモートパスの先頭に共有名を含めます。libsmb2を直接使う現在の構成を維持し、GVfsや共有のマウントは使用しません。SMBでのSSH proxyはexperimental機能として扱い、共有一覧の取得と複数共有の利用も動作確認します。

各段階でビルド・実行できる成果物を作り、検証結果をこの計画へ追記します。保留中のシステムlibsmb2の利用とバージョン別フォールバックは、この計画の対象外です。

## 転送設定ダイアログの配色

転送ウインドウの設定ダイアログにも端末の設定ダイアログと同じ配色規則を適用します。タイトル部分、内容部分、入力部品、ドロップダウンを対象にし、接続で有効になっている色を開いた時点から表示します。

Applyで色を変更した場合は、転送ウインドウと開いたままの設定ダイアログを更新します。カスタム色から既定色へ戻す操作にも対応します。設定の継承元に応じた色の決定は既存の設定処理を使い、転送側だけ別の規則を設けません。

配色処理は既存の端末側を基準にし、必要な部分を共通化します。ダイアログを閉じる際は配色の登録を解除し、開き直しやApplyの繰り返しで古い色や参照が残らないようにします。Applyは開いたまま、Save成功時は閉じる、Cancelは最後のApply以降の未適用値を破棄する既存の動作を維持します。

## 全接続方式の再接続

### 対象と表示条件

「Close window when session ends」を無効にし、切断後もウインドウを残す場合を対象にします。

| 接続方式 | ボタンから開始する操作 |
| --- | --- |
| SSH・Telnet | 接続と必要な認証をやり直します |
| シリアル | デバイスを再オープンします |
| ローカルシェル | シェルまたは設定したコマンドを新たに起動します |
| SFTP | SSHとSFTPを再接続します。SSH端末から開いた転送ウインドウも含めます |
| FTP・FTPS・WebDAV・SMB | 各方式の接続と必要な認証をやり直します |

接続中はボタンを表示せず、切断するとオーバーレイに表示します。古い接続や転送の後片付けが終わるまでは押せない状態にし、操作可能になったら有効にします。再接続中の連打で接続を重複して開始しないようにします。

シリアルでキャリア信号だけが落ちた場合は、受信のためにポートを開いたままにする既存の動作を維持します。この状態では再接続ボタンから旧ポートの終了を要求し、終了完了後に開き直します。転送側も再接続要求で旧操作をキャンセルし、その終了を待ってから新しい接続を開始します。

再接続に失敗した場合は理由を表示し、同じウインドウで再試行できる状態へ戻します。接続・認証中にウインドウを閉じた場合は処理をキャンセルし、遅れた完了通知が破棄済みの画面や新しい接続へ影響しないようにします。自動再接続や中断した転送の自動再開は追加しません。

自動クローズを有効にした場合の既存の終了動作は維持します。シリアルには自動クローズを有効にしてもウインドウを残す既存の例外がありますが、この計画で統一する表示条件は自動クローズを無効にした場合です。初回接続失敗時の画面仕様は変更対象に含めず、切断後に行った再接続の失敗と区別します。

### SSHと共有SFTPの確認

SSHは正常に接続した後のログアウトと通信断で、接続状態、終了処理の完了、オーバーレイ、ボタンの表示・有効状態を追います。既存の接続失敗後の再試行テストだけで完了としません。

SSH端末から開くSFTPは、端末の終了と共有SSH接続の切断を区別します。共有接続が生きていれば利用を継続し、共有接続が切れた場合は転送側にも切断を反映します。現在の再接続処理は独立したSSH接続を開くため、その動作と端末側への影響を確認します。

## SMB共有ブラウズ

### パスと設定

リモート側の`/`を、設定したサーバーの共有一覧を表す仮想ルートにします。共有名はサーバーが公開するフォルダーの名前です。

| リモートパス | 意味 |
| --- | --- |
| `/` | ファイル共有の一覧 |
| `/Public` | Public共有のルート |
| `/Public/documents` | Public共有内のdocumentsディレクトリ |

既定のリモートパスは`/`です。共有を開く操作、共有内の移動、親へ戻る操作、ツリーの展開、パスの直接入力で同じ対応関係を使います。共有のルートで親へ戻ると、サーバーの共有一覧を表示します。

共有名の独立した設定を削除し、接続設定・既定値・保存・入力検証・設定画面・説明文・翻訳を新しいパス仕様に合わせます。旧設定の自動移行や後方互換処理は追加しません。既存の接続を使う場合にリモートパスへ共有名を含める必要があることは、利用者向けの説明に記載します。

### 共有一覧の取得とエラー

同梱libsmb2の`smb2_share_enum_async()`で共有一覧を取得します。公式READMEと公開APIコメントでは、`IPC$`へ接続して共有情報を取得する方式が説明されています。`IPC$`は共有一覧などのサーバー情報を取得するための共有です。名前・種類・説明を取得できるlevel 1を使う方針です。[公式README][libsmb2-readme]と[APIコメント][libsmb2-share-enum-api]を参照します。

一覧にはディスク共有を表示し、プリンター共有と`IPC$`を除外します。共有名が取得できても、その内容を閲覧できるとは限りません。共有を開く際のアクセス拒否は、その共有に対するエラーとして扱い、ほかの共有を利用できる状態を保ちます。アクセス制限を接続全体の切断と誤認しないようにします。

サーバーが共有列挙を拒否しても、既知の共有へ直接アクセスできる場合があります。初期パスや入力したパスが`/共有名/…`なら、一覧の取得成功を接続の前提にせず、その共有へのアクセスを試します。`/`で列挙に失敗した場合は、空の共有一覧として表示せず理由を示します。

列挙APIの完了通知には、通常の負のエラー値に加えて、正のWindowsエラー値が返る場合があります。返された共有情報の解放を含め、列挙専用の応答処理を用意します。既存のSMB操作のエラー判定をそのまま流用しません。[APIコメント][libsmb2-share-enum-api]が出典です。

大量の共有で一覧が途中までしか返らない場合も検出します。同梱APIには列挙を続ける位置の指定がなく、不完全な結果を全件取得済みとして扱えません。事前検証で制約を記録し、外部コードを変更せずに対応できる範囲を確定します。[列挙実装][libsmb2-share-enum-impl]と[MicrosoftのNetShareEnum説明][net-share-enum]を参照します。

### 共有ごとの接続と操作

サーバー全体を表す`RemoteFileClient`から、必要に応じて共有ごとのクライアントへ処理を委譲する構成を基本にします。`/Public/documents`をPublic共有と共有内の`/documents`へ分け、既存のSMBファイル操作を利用します。共有列挙用の`IPC$`接続と、ファイル操作用の接続を分けて管理します。

読み書き中のファイルはその共有への接続を保持します。転送中に別共有を展開しても、接続先やファイルハンドルが切り替わらないようにします。再接続と終了時は、関連する操作の終了を待ってから各接続を解放します。パスの正規化、共有内でのリンク追跡の制限、一時ファイルからのアップロード確定など、既存の動作を維持します。

サーバーの仮想ルートへファイルをアップロードしたり、共有を作成したりする操作は提供しません。共有自体の名前変更・削除も禁止します。共有内のフォルダー作成、名前変更、削除、再帰転送は引き続き利用できます。

共有を通常のディレクトリと同じように再帰削除へ渡すと、共有自体の削除を拒否する前に内容を削除してしまいます。画面の操作可否と転送エンジンの事前判定をそろえ、子の処理へ入る前に共有自体の変更を拒否します。必要な操作可否はパスまたは項目ごとに表現し、クライアント全体の書き込み可否だけでは判断しません。

共有をまたぐ名前変更やアップロードの確定は、同じ共有内の操作と区別します。対応しない操作は理由を示して拒否し、コピーと削除への暗黙の置き換えは行いません。ネットワーク全体のサーバー探索、DFSによる別サーバーへの移動、共有の管理機能は対象外です。

### SSH proxy

共有一覧と複数共有を利用するため、現在の1本だけの中継を複数のSMB接続に対応させます。認証済みのSSH接続を使って、必要なTCP中継チャネルを開く構成を基本にします。共有を展開するたびにSSH認証を繰り返す設計は避けます。

中継先は設定したSMBサーバーとポートに固定し、ローカルの待受はループバックに限定します。直接接続への自動切り替えは行いません。認証情報の保持、切断通知、キャンセル、再接続、終了時の全チャネル解放を複数共有でも成立させます。

共有への接続が成功した既存の検証結果だけでは、`IPC$`経由の共有列挙も成功すると判断できません。直接接続とSSH proxy経由の両方で共有一覧の取得を試し、SambaとWindows 11で結果を記録します。experimentalの表示を維持し、確認できていないサーバーを対応済みと記載しません。

認証失敗と共有へのアクセス拒否はどちらもerrnoの`EACCES`になり得るため、libsmb2の公開APIが返す元のサーバー状態も使って区別します。認証と通信の失敗は共通の接続エラー画面へ戻し、共有のアクセス拒否や未提供の共有は別のパスを試せる状態にします。共有列挙自体の成功は引き続き接続の前提にしません。[公開API](https://github.com/sahlberg/libsmb2/blob/727feaaa6d0f4fed1bae57745fbc2c5db9a30e64/include/smb2/libsmb2.h)と[エラー状態の取得実装](https://github.com/sahlberg/libsmb2/blob/727feaaa6d0f4fed1bae57745fbc2c5db9a30e64/lib/init.c)を照合しました。

同じ共有ブラウズ用ドライバーをメモリ検査付きでリンクする恒久テストを追加し、修正前の失敗と修正後の通過を確認しました。SSH proxy関連のネイティブテスト4件とSMBのGUIテスト2件も通過し、ビルド警告はありません。Windowsでも直接接続・SSH proxy経由のドライバーとGUIテストを再実行し、試験環境の削除とagent-roverの解放まで通過しました。メモリ検査は対応するコンパイラーで全体テストに含めます。リンク時の指定は[GCCのLeakSanitizer説明](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html#index-fsanitize_003dleak)に従っています。

共通側のスキップ6件はGTKのAPI対応状況を指定する5件とGNOMEデスクトップを指定する1件です。ランチャーの1件はDebian trixieのi386パッケージ試験、ネイティブの2件は使い捨て環境で実行するvsftpdとApache WebDAVの試験です。端末側の4件は追加のGTK環境を使うWaylandアイコン試験です。いずれも環境を指定した場合に実行する既存の条件付き試験です。

ビルド警告はありませんでした。性能テストの隔離D-Busセッションでは、GVfsのFUSEマウント拒否とセッション終了時のバス接続エラーが出力されました。各検証は成功し、性能テスト全体も終了コード0でした。この出力は端末の測定用GUIを起動した際のもので、SMBの転送には引き続きlibsmb2を直接使用します。

試験後に実行中のPodmanコンテナーがないことを確認しました。Windowsの試験環境の削除とagent-roverの解放も、最後の直接接続・SSH proxy試験で確認済みです。外部ライブラリの参照とコードは変更していません。利用者向けの日本語・英語の説明を最終実装に合わせ、完了条件9項目を照合しました。変更は`feature/plan13`へ段階ごとにコミットし、mainへはマージしていません。
