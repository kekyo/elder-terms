# plan12：起動中ウインドウのトレイ表示、Applyの継続操作、SMB転送

作成日：2026年10月29日

状態：計画を保存しました。製品コードの変更と機能検証は未着手です。

## 目的と合意事項

システムトレイから、ランチャーが追跡しているターミナルと転送ウインドウを確認できるようにします。設定画面の変更は、Apply後も画面を開いたままにして、変更と確認を繰り返せるようにするものです。

ファイル転送にはSMBを追加します。SMBは、WindowsやNASなどのファイル共有へアクセスするためのプロトコルです。GVfsや共有のマウントを使わず、アプリからlibsmb2を直接利用します。利用者はlibsmb2案と、本実装の前に機能検証を行う方針に同意しています。

Windows共有の検証には、利用者が指定したagent-roverの`win11`セクションを使います。Windows 11側で試験用共有を公開し、Linux側で動かす検証ドライバーとelder-termsからアクセスする構成です。

実装順は、Applyの変更、トレイ一覧と表示操作、SMBの事前検証、SMBの画面統合、全体確認とします。各段階で実行できる成果物を作り、検証結果をこの計画へ追記します。

## 起動中ウインドウの仕様

### 一覧の対象と表示

保存済みの「接続」とは別に、「起動中のウインドウ」サブメニューを追加します。表示内容は、接続名、接続アイコン、ターミナルまたは転送の種別です。対象がない場合は、操作できない空状態の項目を表示します。

対象は、そのランチャーから起動して追跡中の子プロセスです。同じ接続を複数起動した場合も、起動ごとに一つの項目を作ります。表示順は起動順です。同名の項目には番号などの表示上の区別を付けます。

内部の識別には起動ごとの固有IDを使います。保存済み接続のID、接続名、メニュー内の位置、PIDだけでは識別しません。未保存の設定から起動した場合も、起動時の有効な接続名とアイコンを保持します。初期対応では起動時の表示情報を使い、端末内の動的タイトルへの追従は対象外です。

直接コマンドで起動したウインドウと、ランチャー再起動前のウインドウは一覧へ復元しません。SSHターミナルから開くSFTPウインドウも対象外です。このSFTPウインドウは端末と同じプロセス内にあり、現在のランチャーは個別に追跡していません。

正常終了と異常終了のどちらでも該当項目を削除します。プロセスの起動失敗では項目を残しません。起動中の項目と、表示操作が可能になった項目を区別します。

### 一覧からウインドウを表示する

項目の選択で、その起動に対応する既存ウインドウへ表示要求を送ります。新しい接続は起動しません。プロセス間通信をIPCと呼び、ランチャーと子プロセスの間に表示要求用のIPCを設けます。

現在の制御ソケットはランチャーへの要求を受けるためのもので、子ウインドウの表示要求にはそのまま使えません。Unix domain socketまたはD-Busを候補とし、既存の起動・終了管理に合わせて方式を決めます。起動IDと通信先を対応付け、子側から表示準備の完了を通知できる構成にします。

トレイでの操作時刻とactivation tokenを、取得できる場合は子側へ渡します。activation tokenは、利用者の操作を契機にウインドウを表示するための情報です。子側は自分のGTKウインドウへ表示要求を行います。最終的なフォーカス移動はデスクトップ環境に依存するため、X11とWaylandで実際の結果を確認します。

メニューを開いた後の終了と、通信中の終了も検証対象です。古い項目から別の起動へ要求を送らず、終了済みの対象に対する要求を無害に終えます。ランチャー終了後も子ウインドウを使える現在の動作を維持します。

## Apply、Save、Cancelの仕様

| 操作 | 変更後の動作 |
| --- | --- |
| Apply | 現在のウインドウへ適用し、設定画面を開いたままにします。設定ファイルには保存しません |
| Save | 適用と保存に成功したら設定画面を閉じます |
| Cancelまたは閉じる | 最後のApply以降に編集した未適用の値を破棄します。適用済みの値は戻しません |
| 適用失敗・保存失敗 | 設定画面を開いたままにし、失敗理由を確認できるようにします |

対象はターミナルと、独立した転送ウインドウ、SSHターミナルから開く転送ウインドウです。ランチャーのアプリケーション設定と接続の既定値は、現在Saveで保存する画面なので、今回のApply変更の対象には含めません。

ターミナルでは、成功後に閉じる条件をSave時に限定します。転送側では、共通の表示反映処理から閉じる処理を分け、Save成功時だけ閉じます。共通設定ウィジェットが持つ適用済みの値を利用し、状態管理を重複して追加しません。

Apply後の再編集、再Apply、Saveを検証します。保存先のない起動、適用中の連打、背景画像などの非同期読み込み中に閉じる操作も確認対象です。設定画面が残ることに加えて、実際のウインドウへ設定が反映されたことを確かめます。

## SMBの方式選定と対応範囲

### 比較した方式と採用理由

| 方式 | 検討結果 |
| --- | --- |
| libsmb2を直接利用 | 採用します。SMB2/3と非同期APIがあり、既存のcardioによる処理へ組み込む方針に合います |
| Sambaのlibsmbclient | 公開APIにファイル操作が揃っています。ただし同期型のため、UIを止めない実行方式とキャンセル設計が必要です。採用するなら補助プロセスとの通信が候補になります |
| smbclientコマンド | GVfsやマウントなしで利用できますが、出力解析、ファイル名、進捗とエラーの構造化が既存の転送APIに合いません |
| SMBプロトコルの独自実装 | 認証、署名、暗号化、再接続まで保守対象になるため、今回の機能追加には採用しません |
| 既存libcurlのSMB機能 | 調査時の公式説明はSMB1対応です。今回のSMB2/3対応には採用しません |

libsmb2の公式READMEは、高水準の非同期APIを推奨しています。ソケットと監視イベントの変更通知や、低水準の操作も公開APIです。ライセンスはLGPL-2.1系です。[公式README][libsmb2-readme]と[公開APIのコメント][libsmb2-api]を確認して使用します。

libsmbclientのファイル操作は[公式マニュアル][libsmbclient-man]と[公開ヘッダー][libsmbclient-api]を参照しました。公開ヘッダーはGPL-3.0以降の表記で、現在のMITプロジェクトへの組み込み・配布条件も選定項目になります。コマンド方式とcurlの対応範囲は、[smbclientのマニュアル][smbclient-man]と[curlのマニュアル][curl-man]が出典です。

### 初期対応の利用方法

接続種別にSMBを追加し、ホストと共有名を指定して接続します。共有名はサーバーが公開しているフォルダーの名前です。一つの接続で一つの共有を開き、共有内のファイルを既存の転送画面で操作します。

| 設定・機能 | 方針 |
| --- | --- |
| 接続先 | ホスト、ポート、共有名を指定します。通常のTCP接続を使います |
| 認証 | ドメインとユーザー名を設定でき、パスワードは接続時に入力します。設定ファイルには保存しません |
| 初期表示 | ローカル側と共有内の初期ディレクトリを指定できます |
| プロトコル | SMB2/3を対象にし、SMB1へ自動で切り替えません |
| 署名・暗号化 | 方針を設定できるようにします。対応API、既定値、サーバーとの組み合わせは事前検証で確定します。必須にした条件を満たせない接続は失敗として扱います |
| 転送と操作 | 一覧、ダウンロード、アップロード、再帰転送、フォルダー作成、名前変更、削除、進捗、競合確認、キャンセルを既存の操作へ統合します |
| 任意の属性 | 更新日時などは確認できた機能だけを有効にします。POSIX権限やリンク作成を一律に対応済みとしません |

初期の認証方式は、ユーザー名とパスワードによる方式です。Kerberos認証、ネットワーク全体のサーバー探索、サーバーの共有一覧からの選択は今回の範囲外とします。

SMB用の`RemoteFileClient`を実装し、既存の二画面表示と転送エンジンを使います。接続設定の保存・継承・入力検証・翻訳も統合の対象です。SMBを転送用プロセスへ振り分け、トレイでも転送ウインドウとして扱います。

## SMBで事前に検証する点

### 非同期処理と名前解決

cardioでソケットの読み書き可能状態を待ち、libsmb2へ通知する構成を試します。監視対象の変更、接続期限、無応答、処理完了時の監視解除を確認します。待機用のポーリングや安易なワーカースレッド追加で対応しません。

調査したlibsmb2の[接続実装][libsmb2-socket]には、同期`getaddrinfo`による名前解決があります。非同期APIの呼び出しだけでは、DNS待ちでUIを止めないことを保証できません。事前に非同期で名前解決する経路を検証し、ホスト名と接続先アドレスの扱いを確定します。

キャンセル後に遅れて届く完了通知と、セッションやファイルハンドルの寿命を確認します。処理中止のために接続を閉じる必要がある場合は、その後の再接続と画面表示まで含めて結果を記録します。途中まで書き込めたことと、転送が成功したことを区別します。

### 一時ファイルと上書き確定

既存エンジンでは、送信先と同じディレクトリに一時ファイルを作り、送信完了後に本来の名前へ変更します。`upload_commit`は、上書き可否を指定して転送を確定できるという機能情報です。これを有効にする場合は、一時ファイルを排他的に作成し、自分が作成したことを確認する必要があります。

調査したlibsmb2の[通常rename実装][libsmb2-operations]では、置換指定が無効になっています。通常の名前変更には利用できるものの、上書き確定には別の方法が必要です。公開の低水準APIによる置換を検証し、既存の転送先を先に削除する方式へ安易に変更しません。

競合が起きた場合の上書き・スキップ・中止を確認します。転送の途中で失敗した場合は、作成を確認できた一時ファイルだけを後始末します。接続断などで作成結果が分からないときは、他者のファイルを削除せず、確認が必要なパスを利用者へ示す既存の契約に合わせます。

### パス、属性、Windows固有の状態

共有内のパスを、既存画面で使うリモートパスへ変換します。共有のルート、親ディレクトリ、区切り文字、日本語名、空白を含む名前、大文字小文字の違いを確認します。共有外へ移動するようなパスは受け付けません。

Windowsには、リンクやジャンクションなどを表すreparse pointという属性があります。これを通常のディレクトリとして無条件にたどると、再帰転送や削除の対象が変わります。リンクをたどらず属性を調べる既存APIの契約に合わせ、対応できない種類の扱いを事前検証で定めます。

使用中のファイル、読み取り専用ファイル、権限不足、存在しない共有、認証失敗も確認します。更新日時の精度や適用可能な属性は、SambaとWindowsの実際の結果から機能情報へ反映します。

### 依存バージョンと配布

事前検証ではlibsmb2の使用バージョンと必要な公開APIを記録します。公式文書とAPIコメントを確認し、非推奨APIや内部APIは使いません。上流のソースやベンダーコードは編集しません。

検証したバージョンを基に、対象のUbuntu/Debian環境での導入方法を決めます。共有ライブラリとしての利用を基本に、実行時依存、ライセンス文書、配布パッケージでの導入を確認します。ライブラリの不足や版の不一致を検出できることも必要です。

## Windows共有の検証環境

agent-roverの`win11`セクションへ接続し、Windows 11側に試験専用のディレクトリと共有を用意します。Linux側から到達できる共有先と、試験用の認証情報を使います。検証するのはLinux版クライアントからWindows共有へのアクセスであり、Windows版elder-termsの開発ではありません。

接続前にagent-roverの公式ドキュメントと、利用するAPIのコメントを確認します。セッションが使用中なら接続できるまで待ちます。待機中はWindowsを使わない検証や文書整理を進め、無理に別セッションへ切り替えません。

共有と試験データは既存のものと区別します。共有の公開や必要な権限設定では、作成したものと変更前の状態を記録します。認証情報をコミットや試験結果へ含めません。

検証ドライバーから一覧と読み書きを試し、製品への統合後は同じ共有へ転送画面から接続します。ファイル内容、名前変更と削除の結果、一時ファイルの状態はWindows側でも確認します。使用中ファイルやリンクの条件もWindows側で準備します。

成功・失敗のどちらでも、試験用ハンドルを閉じ、試験用共有とデータを片付けます。今回変更した設定があれば元に戻します。試験本体と後片付けが終わったら速やかにセッションを解放し、ログ整理のために占有を続けません。共有を用意できなかった場合は未検証として記録し、Windows検証済みとは扱いません。

## 実施段階と完了条件

### 段階1：Apply後も設定画面を保持する

ターミナルと転送ウインドウで、Apply後も設定画面が残り、実際の表示が変わる試験を追加します。現状で失敗することを確認してから、閉じる処理をSave成功時へ限定します。

試験ではApply、再編集、再Apply、Saveの順に操作します。Apply後のCancel、保存失敗、保存先のない起動も確認対象です。設定画面が閉じることを前提にした既存試験は、新しい動作へ合わせます。

成果物は、設定を繰り返し調整できるアプリと回帰試験です。対象試験が成功し、端末と独立・内蔵の転送画面で操作の意味が一致したら完了です。`fix:`でコミットします。

### 段階2：追跡中の子プロセスをトレイへ表示する

追跡情報に追加するのは、起動ごとの固有ID、表示名、アイコン、種別です。起動と終了による一覧更新の試験を先に作り、失敗を確認してから実装します。

SNI/D-BusMenuとXEmbedの両方に一覧を追加します。同名の複数起動、未保存設定での起動、正常終了、異常終了、起動失敗、トレイ方式の再選択を確認します。この段階では一覧表示までを成果物とし、子側の表示準備が未対応の項目を操作可能にしません。

成果物は、実際の起動・終了に追従するトレイ一覧です。両方式で同じ対象が表示され、終了した起動だけが消えることを完了条件にします。`feat:`でコミットします。

### 段階3：選択したウインドウへ表示要求を送る

追加するのは、起動IDに対応するIPCと子側の表示処理です。表示準備の通知と、トレイ操作の情報を渡す経路を設けます。通知と終了の競合を再現する試験を先に追加します。

同名の複数起動から選んだウインドウが表示対象になることを確認します。メニュー表示後の終了、起動途中の操作、ランチャー終了、X11とWaylandでの表示結果を検証します。

成果物は、一覧から既存ウインドウを呼び出せるアプリです。別の起動へ要求を送らず、対象の終了時にも正常に処理できることを完了条件にします。デスクトップ環境による差は結果として記録し、`feat:`でコミットします。

### 段階4：libsmb2の実行可能な検証ドライバーを作る

現在のプロジェクト内に、小さなC++の検証ドライバーと再現手順を追加します。接続と一覧を実行できる状態から始め、読み書き、フォルダー作成、名前変更、削除、上書き確定を順に検証します。各操作には実際の内容や結果を確認する試験を用意します。

cardioとの接続、名前解決、タイムアウト、キャンセル、接続断、後始末を確認します。LinuxのSamba共有と、agent-roverの`win11`セクションで公開した共有の双方を対象にします。再帰転送に必要なパスと属性の意味も、この段階で確かめます。

成果物は、繰り返し実行できるドライバー、試験、検証結果です。使用バージョン、両サーバーの条件、成功・失敗、採用するAPI、残る制約を記録します。`RemoteFileClient`の契約を満たす方法を説明できたら完了です。検証コードは`chore:`、結果の記録は`doc:`で適切に分けてコミットします。

必要な機能を公開APIで実現できなかった場合は、対応したことにせず、原因と代案を計画へ反映します。採用方式や合意済みの機能範囲を変える必要がある場合は、その判断を確認してから依存する実装へ進みます。

### 段階5：SMB接続と一覧・ダウンロードを画面へ統合する

事前検証で選んだ方式を使い、SMB用の設定、起動処理、クライアントを追加します。設定の保存・継承・入力検証と、転送用プロセスへの振り分けを試験で確認してから実装します。

既存画面で認証し、共有内の一覧を開き、ファイルとディレクトリをダウンロードできる状態にします。進捗、競合確認、失敗表示、キャンセルも含めます。この途中段階で未対応の変更操作は有効にしません。

成果物は、保存したSMB接続から共有を参照し、ダウンロードできるアプリです。SambaとWindows共有の両方で内容を確認でき、トレイと設定画面も使えることを完了条件にします。`feat:`でコミットします。

### 段階6：アップロードと変更操作を統合する

この段階の対象は、アップロード、再帰転送、フォルダー作成、名前変更、削除です。一時ファイルの排他的作成、上書き確定、競合、中止、失敗時の後始末を、既存エンジンの契約に従って実装します。

大文字小文字、日本語名、空ファイル、大きなファイル、使用中のファイル、権限不足、リンクの扱いを検証します。接続断やキャンセルの後にも、表示と操作が一貫し、必要な再接続を行えることを確認します。

成果物は、今回の対応範囲を備えたSMB転送機能です。両サーバーで転送内容と変更操作の結果が一致し、不明な一時ファイルを誤って削除しないことを完了条件にします。意味のある操作単位で`feat:`または`fix:`のコミットを作ります。

### 段階7：配布と全体動作を確認する

libsmb2の導入と配布依存を整え、配布パッケージから起動できることを確認します。新しい設定とメニューの翻訳を追加します。利用者向けには、SMBの接続方法、対象範囲、Applyの動作を日本語で説明し、それを原本として他言語へ反映します。一般文書からこの計画書へのリンクは追加しません。

Applyとトレイの最終確認に加え、SFTP・FTP・FTPS・WebDAVの回帰試験を行います。ビルド警告は原因を調べて対処し、ルートの`npm test --workspaces`で全体試験を実行します。Windows側の試験用共有を片付け、agent-roverを解放したことも確認します。

成果物は、配布可能なアプリ、利用者向け文書、全体試験の結果です。下表の完了条件と実施結果を照らし合わせ、未確認項目を残して完了扱いにしません。変更に応じて`chore:`または`doc:`でコミットします。

## 試験と作業の共通方針

コード変更では、期待する動作を検証する試験を先に追加し、変更前の失敗と変更後の成功を確認します。ソース文字列の存在確認だけで機能を検証しません。GTK画面は既存のgestamentによる試験を利用します。

非同期処理の試験は、開始・完了通知や制御できる待機点に合わせて操作します。固定時間のsleepだけで競合を再現しません。UIの時間軸の問題を検証する場合は、動画を撮影して挙動をアサートします。期待画像を追加・変更する場合は目視で確認します。

各段階で関連試験とビルドを行い、最終段階では全体試験を省略しません。想定より遅い試験は、処理が進んでいるかを調べてから待機時間を判断します。必要なパッケージの導入に管理者権限が要る場合は、利用者へインストールを依頼します。

サブモジュールやベンダーコードは変更しません。C++はC++20とcardioを使い、既存インターフェイスへの委譲を優先します。自由に選ぶ試験補助スクリプトにはNode.jsを使います。計画外の問題が見つかったら原因と計画を見直し、不要になった修正を残しません。mainへのマージはこの計画に含めません。
