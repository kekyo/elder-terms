# plan30 動作中の端末をタブトレイにまとめ、別ウインドウへ分離する

タブトレイは、複数の端末をタブとして表示するウインドウです。利用者が単独の端末をタブトレイに落とすと、そこで同じシェルの続きを操作できます。タブを外へドラッグすれば、再び単独ウインドウとして使えます。所有権を移すタイミングはドロップを確定した時です。ドラッグ中や取り消し時は元の端末で処理を続けます。最初の対象はLinuxのローカル端末、次に同じ仕組みをSSH接続で試します。

2026年11月24日作成。調査したelder-termsは`bda08f9c`、boxrigは`268522c`です。boxrig側では、端末本体の状態を保存・復元する汎用APIを計画しています。その計画書はboxrigリポジトリの`docs/ja/plans/plan31-cross-process-terminal-handoff.md`です。elder-termsは通信路、表示先、利用者の操作を引き継ぎます。ローカル端末での採用条件は、移動の前後とも通常の入出力を直接行えることです。

## 現在の所有関係

ランチャーは接続ごとに子プロセスを起動し、起動IDと表示先を対にして追跡しています。端末本体、UIモデル、GTKウィジェット、通信の所有者は、端末側の`TerminalRuntime`です。現在はウインドウの終了時に接続とログを止め、端末本体を破棄します。ドッキングには、セッションを閉じる操作と表示先を解放する操作がそれぞれ必要です。[ランチャーの追跡](../../../elder-terms/src/main.cpp#L1704)・[端末の所有関係](../../../elder-terms-terminal/src/terminal-runtime.cpp#L33)・[ウインドウ終了処理](../../../elder-terms-terminal/src/main.cpp#L398)

操作感の基準は、boxrigにある同一プロセス内の移設例です。同じGTKウィジェットを別ウインドウへ移すと、選択・表示設定・接続を維持できます。プロセスが異なる場合は、移動先で端末本体を復元し、GTKウィジェットを生成します。[boxrigのGTK移設仕様](https://github.com/kekyo/boxrig/blob/268522c/docs/ja/platforms/gtk.md#別のウィンドウへ移す)・[往復移設の実例](https://github.com/kekyo/boxrig/blob/268522c/examples/gtk/transfer.c)

## 接続ごとのデータ経路

| 接続 | 通常時と移動後の送受信 | 接続を維持する担当 |
| --- | --- | --- |
| ローカル | 表示中の端末プロセスが疑似端末（PTY）のmasterを直接読み書きする。ドッキング時に限り、Unixドメインソケットの`SCM_RIGHTS`で同じmasterのファイル記述子（FD）を渡す | ウインドウに依存しない親プロセスがシェルを起動し、終了状態を一度だけ回収する |
| SSH | 接続を開いたプロセスに端末がある間は直接送受信する。端末本体が別プロセスに移った間だけ、両プロセス間でデータを中継する | 接続を開いたプロセスが認証済みのチャネル、プロキシ、共有中のSFTP通信を維持する |

PTYのFDを渡すと、移動先から同じシェルに入出力できます。子の終了を待つのは起動した親です。端末を単独起動した場合もこの親が回収を担当し、ランチャーや旧ウインドウを終了した後もシェルを維持します。各プロセスが持つFDは同じPTYを指すため、読み書きとリサイズを許すのは切替前後を通じて一つの所有者だけです。[LinuxのFD転送仕様](https://man7.org/linux/man-pages/man7/unix.7.html)・[子プロセスの終了待ち](https://man7.org/linux/man-pages/man2/waitpid.2.html)・[現在のPTY起動と回収](../../../elder-terms-terminal/src/terminal-connection.cpp#L535)

SSHチャネル、認証、進行中の転送を管理するのは接続元のプロセスです。二度目の移動でも、新しい所有者は同じ接続元と直接やり取りします。中継には容量を制限したキューを使い、読み書きが可能になった時に処理します。少量の入力はすぐに送り、大量出力でまとめて送るのは既に届いた分だけです。チャンクごとの往復確認やタイマー待ちは設けません。[SSHチャネルの所有者](../../../elder-terms-terminal/src/terminal-ssh-transport.cpp)・[SSHを共有するSFTPウインドウ](../../../elder-terms-terminal/src/main.cpp#L423)

全接続を常時中継する案なら寿命の管理を統一できますが、未移動の端末でもキー入力とエコーがそれぞれプロセス境界を越えます。もう一案は、接続とboxrig本体を同じプロセスに置き続け、可視行・画像の更新と入力を表示先に転送する方式です。履歴が大きい場合でも移動時のコピーを減らせる一方、選択・スクロール・入力・アクセシビリティを含むリモート表示APIが必要です。今回のパイロットでは端末本体が実際に別プロセスへ移る方式を評価します。[boxrigのモデルと表示先の契約](https://github.com/kekyo/boxrig/blob/268522c/include/boxrig/ui/view.h#L1077)

## 切替の手順と失敗時の扱い

セッションにはウインドウやPIDから独立したIDを割り当てます。セッションごとに記録するのは、現在の所有者と切替を確定するたびに進む世代番号です。ランチャーの「表示」はこのIDから現在の所有者を引き、単独ウインドウを前面に出すか、トレイ内の該当タブを選びます。

1. ドロップ先に表示枠を用意します。元の所有者は新しい入力とリサイズの受付を止め、進行中の非同期読み書きがどこまで完了したかを確定します。PTYでは旧FDの監視を解除し、その先の受信はカーネルのPTYバッファに残します。SSHでは接続元が切替境界以後のデータを上限付きで保持し、満杯なら上位への読み出しを待ちます。
2. 端末を再開するために保存したデータをチェックポイントと呼びます。旧所有者はboxrigのチェックポイントに、アプリ側で保持した未処理の入出力と表示設定を対応づけます。端末に投入済みの範囲、接続先への書き込み済みの範囲、ログやマクロに通知済みの範囲を区別し、各バイトの続きを一度だけ処理できるようにします。
3. 新所有者は元の行数・桁数で端末を復元し、表示枠に最初のフレームを用意します。確定まではPTYのFDを受け取っていても入出力を始めません。管理側が所有世代を一度だけ更新してから新所有者が送受信を開始し、フォーカスを受け取ります。新しい配置で行・桁数が変わった時だけ接続先へ通知し、旧表示を解放します。
4. 確定前に表示先を失った場合は、旧所有者が同じ境界から再開します。確定通知を失った参加者は管理側に世代を問い合わせます。確定後の旧所有者には再開させません。PTY終了やSSH切断が切替と重なった場合も、最後の出力と終了理由をその世代の表示先に届けます。

主画面・代替画面・履歴・パーサの途中状態・未送信の端末応答は、boxrigのチェックポイントに含まれる状態です。elder-termsには別に、文字コード変換器の状態、変換済みで未投入のバイト、未送信キュー、実行途中の受信マクロがあります。PTYの直接移設では復元可能な変換状態と未処理分を引き継ぎます。状態を復元できない文字コードや操作では、元の端末で通信を続けます。操作完了で移せるものは完了通知で再試行します。SSHで接続元に残すのは変換器、ログ、進行中のファイル転送です。移動先には進捗表示と操作を引き継ぎます。[送受信と変換の状態](../../../elder-terms-terminal/src/terminal-connection.cpp#L63)・[文字コード変換器](../../../elder-terms-terminal/src/terminal-sessions/terminal-text-stream.cpp#L25)・[受信マクロ](../../../elder-terms-terminal/src/terminal-received-macros.cpp#L31)

表示先にはタイトルとその履歴、設定とズーム、確定済みの選択範囲を引き継ぎます。選択の両端を表すのは、論理テキスト上の位置です。入力メソッドの未確定入力は既存のGTK移設規約に合わせて終了し、開始済みの貼り付けは末尾まで一度だけ届けます。ドラッグ中にドロップ候補を通過しても、接続先の行・桁数やタイトルはそこで変更しません。[GTK移設時の入力と貼り付け](https://github.com/kekyo/boxrig/blob/268522c/docs/ja/platforms/gtk.md#L101)

## 実装段階と完了条件

### 30.1 同じプロセスで単独ウインドウとタブを往復する

セッションと表示先の寿命を分け、既存のGTK移設機能で使えるタブトレイを作ります。一つのプロセスに二つの端末を開き、指定した端末だけをドック・分離します。この段階に必要な機能は現行のboxrigで利用可能です。

完了条件は、移設した端末で同じシェルに入力でき、移動元ウインドウを閉じてもログと受信が続くことです。もう一方のタブの選択、タイトル、接続も照合します。取り消し、トレイからの再分離、ランチャーからの再表示を実際のUIで試します。

### 30.2 ローカルPTYを別プロセスへ直接引き渡す

この段階から使うのは、boxrigのplan31で検証した公開APIです。通常ビルドと配布用SDKに同じ版を取り込みます。最初の試験は、UTF-8のシェルを単独ウインドウから別プロセスのトレイへ移し、元へ戻す操作です。旧UIプロセスを終了できる構成にし、シェルの起動・終了回収とFDの直接入出力を確かめます。

完了条件は、往復してもシェルPIDが同じで、連番出力、端末からの応答、入力、ログに欠落と重複がないことです。代替画面から戻った時の履歴、選択、貼り付け、出力中のサイズ変更も照合します。確定直前に移動先を終了する試験と、確定通知を再送する試験で、一方の端末だけが操作を続けられることを確認します。

### 30.3 SSHは接続元を保ち、移動時だけ中継する

この段階の対象は、認証を終えてシェルを操作できるSSH接続です。チャネルを開いたまま端末本体をトレイへ移します。完了条件は、再認証を要求されず、連続出力とキーへの応答が続くことです。転送中に往復してファイルの内容、進捗、ログを照合します。共有中のSFTPウインドウが同じ接続で操作でき、タブを続けて移しても中継段数が増えないことを確かめます。[転送の既存試験](../../../elder-terms-terminal/tests/boxrig-transfer.test.ts)

### 30.4 通常時の速度と移動時の停止を測る

現行の軽負荷試験には、10キーの子プロセス到達が中央値1.125 ms、画素を初めて観測するまでが中央値16.512 msという記録があります。画素の観測間隔は約16 msです。これは過去の直接接続の値で、中継やドッキングの増分は未測定です。現行のI/O処理では既定で4 KiBずつ読み出します。仮に毎秒10 MiBを4 KiBごとに送ると、中継は毎秒2,560回です。この計算例を踏まえ、実際のチャンク長と送信回数も記録します。[既存の入力遅延測定](plan11-terminal-input-latency.md#段階1の計測基盤)・[ローカル接続の既定値](../../../elder-terms-terminal/src/terminal-connection.h#L42)

| 比較するもの | 測定方法 |
| --- | --- |
| 1キーの応答 | キー送出から相手への到達、相手の出力から端末への投入、画面での初見を別々に測る。無出力時と連続出力中の中央値・p95を比較する |
| 大量出力 | 同じデータと端末寸法で処理量（MiB/s）、関係する全プロセスの合計CPU時間、キューの最大使用量を比較する |
| ドック・分離 | ドロップ確定から初回描画、入力受付停止から再開までを測る。通常画面、履歴上限付近、画像を含む画面で転送量と経過時間を記録する |

同じマシンで現行版と試作版を交互に実行します。比較対象は、ローカルPTYなら移動前と移動後の直接経路、SSHなら直結と移動後の中継です。既存ドライバーのLocal・SSH、Cairo・OpenGLの条件を再利用し、描画待ちと通信待ちを切り分けます。通常時のPTY本文が中継を通らないことを確認し、直接経路で反復測定のばらつきを超える悪化があれば、その区間を特定して再比較します。SSHで採用を判断する材料は、中継で増える通常時の負荷と、ドロップ時の停止時間を別々に測った結果です。[測定ドライバー](../../../elder-terms-terminal/tests/performance/run-latency.mts#L23)

各段階で先に試験にするのは、利用者から観測できる振る舞いです。変更前の失敗と変更後の成功を確認します。最終確認ではX11とWaylandで実際のドック・分離を動画に記録し、フォーカス、初回描画、サイズ通知の順を照合します。パイロットの完了条件は、各段階の確認と性能比較を終え、警告を解消したうえで`make build`と`make test`が成功することです。
