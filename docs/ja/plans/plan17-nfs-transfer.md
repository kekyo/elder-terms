# plan17：NFS v2・v3・v4のファイル転送

作成日：2026年11月2日

状態：計画作成。実装は未着手です。NFS v2の補完と、NFS v4専用サーバーの公開ルート探索を段階的に検証します。

## 目的と前提

libnfsを使い、NFSの公開ディレクトリを転送画面から閲覧・送受信できるようにします。exportは、サーバーが外部へ公開するディレクトリです。SMB共有と同様に、各exportをアプリ側のルート直下に置き、その中を通常のディレクトリとして操作します。

NFS v2はlibnfsの低水準RPC APIを使い、アプリ側で不足するファイル操作を補います。外部コードの編集や、NFS v2を実装せずにv3へ切り替える対応は行いません。古いプロトコルを使う判断とそのリスクは、依頼どおり利用者の責任であり、本planの対象外です。

調査基準と共通の実施条件は[plan15](plan15-transfer-jobs-and-tree-icons.md)を参照します。新しい接続種別として追加し、既存SMBの共有ブラウズを変更するための計画にはしません。

## 現在のコードと外部API

[RemoteFileClient](../../../elder-terms-terminal/src/file-transfer/remote-file-client.h)には、一覧、属性、読み書き、変更操作、能力情報が定義されています。[SMBのサーバークライアント](../../../elder-terms-terminal/src/smb/smb-client.cpp)はサーバールートと共有内パスを分け、共有ごとの接続を遅延して開始します。この責任分担をNFSでも使用します。

確認したlibnfsは`affe4c88829cd07bba082fe544df05d89c770d49`です。[公式README](https://github.com/sahlberg/libnfs/blob/affe4c88829cd07bba082fe544df05d89c770d49/README)では高水準の同期・非同期APIとRAW RPC APIを区別しています。[公開ヘッダー](https://github.com/sahlberg/libnfs/blob/affe4c88829cd07bba082fe544df05d89c770d49/include/nfsc/libnfs.h)と[RAW APIのコメント](https://github.com/sahlberg/libnfs/blob/affe4c88829cd07bba082fe544df05d89c770d49/include/nfsc/libnfs-raw.h)も確認しました。採用版は段階1で固定します。

この版の`LIBNFS_API_V2`はライブラリAPIの世代であり、NFSプロトコルv2の意味ではありません。RAW APIには`rpc_nfs2_*_task()`と`rpc_mount1_*_task()`があります。古い例にある`*_async()`の名前や戻り値を混用せず、採用した公開契約で実装します。

| 対象 | 実装方針 |
| --- | --- |
| NFS v3 | libnfsの高水準非同期APIを使う |
| NFS v4 | まずv4.0を必須の検証対象とする。調査版にあるv4.2はビルド条件と実通信を確認し、対応を別表示する。v4.1など未検証のminor versionまで一括して対応済みとしない |
| NFS v2 | RAW RPCでmount、ファイルハンドル解決、列挙、属性、送受信、変更操作を組み立てる |
| 非同期実行 | ソケットのreadinessとRPCの期限をCardioに接続する。libnfsの同期APIや内部ワーカースレッドを通常の実行経路にしない |

## exportsとNFS v4の公開ツリー

NFS v2・v3のexports列挙に使うのはMOUNTプロトコルです。v2にはMOUNT v1、v3には対応するMOUNTの版を使い、汎用の列挙関数が使える組合せをドライバーで確認します。一覧取得の失敗と、既知のexportへ接続できないことを同じ扱いにしません。

NFS v4はMOUNTの機能をNFS本体に統合しており、v4専用サーバーにMOUNTによる完全なexports一覧を要求できません。公開名前空間のルートから探索する方式と、既知の公開パスを登録する方式を用意します。根拠は[RFC 7530の7節](https://www.rfc-editor.org/rfc/rfc7530.html#section-7)です。

| サーバーの応答 | アプリ側のルート |
| --- | --- |
| v2・v3でexportsを列挙できる | 各exportをルート直下に表示する |
| 列挙を拒否するが既知のexportへ接続できる | 設定に登録した公開パスをルート直下に表示し、列挙失敗の理由を示す |
| v4専用で公開名前空間を閲覧できる | アクセス可能な公開パスを候補として表示する。サーバーのexport設定を完全取得したとは表示しない |
| v4の公開ツリーが深い、または途中を一覧できない | 明示されたv4の公開パスを入口として追加する |

v4の名前空間上のパスと、v3のexportパスは別の値として保持します。たとえばv3の`/srv/public`がv4では`/public`になる構成を、同じ文字列と推定して接続しません。v4の公開ツリーの通常ディレクトリも、明示的に入口として選んだ場合は公開ルートとして表示できます。

画面の`/`はサーバーの一覧です。exportの表示名にはサーバー上の絶対パスを使い、操作用パスでは先頭要素を衝突しない識別子へ変換します。初期案はexport全体を一つのURIエンコード済み要素にする方式です。`/srv/public`なら`/%2Fsrv%2Fpublic/file.txt`、`/`なら`/%2F/file.txt`とし、表示名と操作用識別子を混同しません。

同じbasename、入れ子のexports、空白、日本語、`%`を含む名前を区別します。サーバールートとexportそのものの削除・名前変更は禁止し、export内部だけを変更可能にします。別exportへの名前変更は拒否し、コピーによる移動へ自動変換しません。plan15のNFS公開ルートアイコンを適用します。

## NFS v2で補う機能

| 機能 | 補完内容と検証対象 |
| --- | --- |
| 接続と公開ルート | PORTMAP/RPCBIND、MOUNT v1、取得したルートハンドルの所有と解放 |
| パス解決 | LOOKUPを組み合わせた各要素の解決、GETATTR、存在しない項目、`..`でexportを越えない処理 |
| 一覧 | READDIRのcookieによるページ取得と、必要なGETATTRによる種別・サイズの補完 |
| 受信 | READのオフセットと分割転送、短い応答、EOF、ゼロバイト |
| 送信 | CREATEとWRITE、短い書き込み、エラー後の一時ファイル、完了後のRENAME |
| ディレクトリ・ファイル変更 | MKDIR、RMDIR、REMOVE、RENAMEを共通インターフェイスへ対応させる |
| リンク・属性 | READLINK、SYMLINK、SETATTR。共通エンジンと同じくシンボリックリンクを無条件に再帰追跡しない |
| エラー | RPCの失敗とNFSの応答エラーを分け、アクセス拒否、消失、容量不足、古いハンドルを区別する |

NFS v2のデータ量・オフセット・サイズの表現には制限があります。検査の根拠は[RFC 1094](https://www.rfc-editor.org/rfc/rfc1094.html)と採用するXDR定義です。要求を送る前に範囲を検査し、サーバー固有の上限も分けて検証します。32ビット値を狭い型へ丸めたり、サイズが大きいファイルを成功したように切り詰めたりしません。

v2のCREATEやRENAMEを、排他的作成・上書きなしの原子的操作と仮定しません。共通エンジンが求める一時ファイルの所有証明と照合し、能力フラグには実際に保証できるものだけを返します。不確実な一時ファイルを失敗後に無条件で削除しない契約です。

READDIRが同じcookieを返し続ける場合も検出します。再試行で変更操作を重複実行しないよう、通信終了後の状態が不確実な場合はその事実をジョブ結果へ残します。サーバー再起動後の古いハンドルは破棄し、再接続で公開ルートから取得し直します。

## 接続設定と寿命

設定候補は、ホスト、NFSの版、v2/v3のTCP・UDP、初期公開パス、追加の既知パス、ローカルディレクトリ、UID、GID、補助グループ、接続・要求の期限です。初期の認証は数値IDを渡すAUTH_SYSとし、RPCSEC_GSSなどを対応済みとして表示しません。プロトコルの版を明示した接続では、別の版に自動変更しません。

v2/v3の標準構成ではサービスのポートを探索し、固定ポート指定が必要な構成も段階1で検証します。予約済み送信元ポートを要求するサーバーについては、権限とlibnfsの公開APIで成立する接続方法を確認します。管理者権限が必要な試験環境の準備は、その時点で必要な導入内容を示します。

v3/v4はexportごとのクライアントを遅延して作り、サーバー単位の窓口が列挙とパス解決を担当します。v2も同じ外部契約とし、内部実装の共通化は責任が一致する部分に留めます。切断時は開始済みのコールバックを回収してからRPCコンテキストを破棄します。

SSH proxyは今回の必須対応に含めません。NFSのポート探索やUDPを、現在のSMB向けTCP転送へそのまま接続できるとは見なしません。追加する場合は到達経路を検証した別段階を設けます。

## 段階1：採用APIと実通信の検証ドライバー

外部ソースを変更せずにlibnfsを固定してビルドし、各版を明示するドライバーを作ります。v3・v4.0の一覧と1ファイル受信、v2のMOUNT・LOOKUP・READを動かし、実際に使用したプロトコルの版を確認します。

v2対応サーバー、v3サーバー、MOUNTを提供しないv4専用サーバーを試験環境として確保します。新しいLinux環境でv2が無効な場合は、v2対応の隔離VMなどを用意します。v3の成功をv2の代用にしません。完了条件は、各版の実通信と非同期停止を観測でき、採用版・API・試験環境が確定することです。

## 段階2：NFS v3と公開ルートを画面で利用する

v3の一覧・送受信・変更操作を`RemoteFileClient`へ実装し、設定と転送画面へ組み込みます。公開ルートの衝突しないパス、変更禁止、既知パス、アクセス拒否から別exportへの移動を確認します。

完了条件は、画面から複数exportを扱え、ファイル・ディレクトリを双方向に転送して内容を比較できることです。ここで実際に使える一方式を完成させます。

## 段階3：NFS v4の公開ツリーと転送を統合する

v4.0の公開名前空間と登録パスをアプリ側のルートへ対応させます。MOUNTの有無にかかわらず接続できること、v3と異なるパス、権限拒否、サーバー再起動、状態を保持する接続の終了を検証します。

v4.2を提供する場合は、この段階で専用の設定値と実通信試験を追加します。完了条件は、保証するminor versionが明確で、v4専用サーバーを画面から閲覧・送受信できることです。

## 段階4：NFS v2の閲覧と受信を完成させる

RAW RPCの結果を所有権のある値へ変換し、パス解決、ページ付き一覧、属性、読み取りを実装します。画面へ読み取り専用として接続し、書き込み能力はこの段階では無効にします。

完了条件は、v2だけを提供するサーバーで深いディレクトリを閲覧・再帰受信でき、循環するリンク、READDIRの異常、短いREAD、サイズ上限を正しく扱うことです。

## 段階5：NFS v2の送信と変更操作を完成させる

送信、作成、削除、名前変更、リンクと属性を実装し、確認済みの能力を有効にします。各操作のRED・GREENを確認してから、同じGUIで実行できる状態へ進めます。

完了条件は、v2の双方向転送で内容が一致し、中止・切断・容量不足で成功を誤表示しないことです。exportルートと無関係なファイルを変更しないことも検証します。

## 段階6：版ごとの統合試験と全体検証

全版で複数export、入れ子の公開パス、日本語名、ゼロバイト、読み取り専用、認証ID、長い一覧、再接続、ウインドウ破棄を確認します。v2のTCP・UDPを提供する場合は両方を検証します。上限付近の転送は境界値テストと実通信試験を分けます。

plan15のジョブ結果、アイコン、進捗動画、利用者向け説明を確認し、`make test`を実行します。必要なv2・v4専用試験が未実施なら、その版の完了条件を満たしたとは記録しません。

## 最終完了条件

1. NFS v2・v3・v4.0を明示して接続し、各版で閲覧・送受信・必要な変更操作を実行できる。
2. exportsを衝突しないルート直下の擬似パスとして扱い、ルートそのものを変更できない。
3. v4専用サーバーと列挙拒否のサーバーで、公開ツリーまたは既知パスから操作できる。
4. v2の不足機能をアプリ側で補完し、サイズ制限、RPCの期限、切断、古いハンドルを扱える。
5. 各版の実通信、ジョブ・アイコン、全体テストが通り、外部ソースを変更していない。
