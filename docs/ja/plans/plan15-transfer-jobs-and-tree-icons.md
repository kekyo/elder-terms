## ファイル名の文字コードに関する追加調査

2026年11月2日、`7ba9df61`のコードと採用ライブラリ・プロトコルの仕様を照合しました。対象はファイル転送画面の名前とパスです。端末通信の文字コードや、転送するファイル本文の変換とは分けて扱います。以下は適用要否の調査結果であり、非UTF-8名の実通信試験は各方式の実装段階で行います。

ファイル名・パス用の文字コード設定の製品既定値は、UTF-8に確定します。NFS、FTP/FTPS、SFTPに共通の方針です。グローバル設定、テーマ、接続のいずれにも指定がない場合はUTF-8を使い、明示された設定がある場合は既存の継承順で上書きします。OSのロケールや端末通信の文字コードを、この既定値の代わりに使いません。

| 転送方式 | 名前の文字コード設定の要否 | 現在のコード・推奨する対応 |
| --- | --- | --- |
| NFS v2/v3 | 必要 | plan17へ接続単位の設定を追加する。libnfsへ渡す名前のバイト列とGTK用の表示名を分ける |
| NFS v4 | UTF-8を既定にし、非UTF-8名を受け付けるサーバーへ明示指定を認める | サーバーの拒否を別の符号化で再試行しない。詳細はplan17 |
| FTP/FTPS | 必要 | 現在は非UTF-8の一覧項目で一覧全体をエラーにする。接続ごとの指定とUTF8機能の使用方針を一緒に設計する |
| SFTP | 必要 | 使用中のlibsshはSFTP v3の名前をバイト列として渡す。既存名の保持と、新規名・表示名の変換を加える |
| SMB v2/v3 | 通常は不要 | libsmb2がアプリのUTF-8と通信のUTF-16を変換する。CP932などへ先に変換しない |
| SMB v1・libdsm | NFS型の設定をそのまま追加しない | 公開APIはローカル符号化、内部はUnicode変換を使う。補助プロセスのロケールを制御し、旧来のコードページ（OEM）専用サーバーへの対応可否は別途検証する |
| WebDAV | 通常は不要。非UTF-8のURLパスを持つサーバーへの互換対応では検討が必要 | XMLの文字コードとURL内のバイト列は別。現在のUTF-8パス限定を見直す場合は、元のhrefを識別子として保持する変更が先になる |
| HTTP/HTTPS | NFS型の一律設定は不要 | HTMLの文字コード、URLのバイト列、保存名候補を分ける。宣言のないHTMLや旧形式のURLの表示を補う設定は別の目的として検討する |

### FTP/FTPSとSFTPで必要な対応

[ftp-client.cpp](../../../elder-terms-terminal/src/ftp/ftp-client.cpp)の`directory_snapshot()`は、LIST・MLSDで得た名前へ`g_utf8_validate()`を適用し、失敗すると一覧を返しません。接続時はFEATにUTF8があれば`OPTS UTF8 ON`を試みますが、ファイル名の符号化を選ぶ設定はありません。FTPSも同じクライアントを使うため、暗号化の有無によらず同じ対応が必要です。

[RFC 2640の3節](https://www.rfc-editor.org/rfc/rfc2640.html#section-3)はUTF-8の利用と、別の符号化や未判定のバイト列の扱いを述べています。FTP/FTPSの設定はUTF-8を既定とし、接続ごとの明示指定を認めます。非UTF-8を指定した接続でUTF8を有効にしないこと、UTF8の機能広告と設定コマンドの応答を分けること、必要なら無効化を要求して結果を検証することまで計画します。コマンドの成功だけから、任意の文字コードをサーバーが使用しているとは推定しません。

LIST・MLSDの構造と属性はバイト列のまま解析し、取り出した名前だけを表示用に復号します。PWD、初期パス、MLST、転送、RNFR/RNTO、作成・削除、一時ファイルも同じ符号化境界を使う必要があります。libcurlのURLへ渡す経路では、文字コード変換後のバイト列をパーセント表記にし、FTPコマンドへ渡す経路では実際のバイト列を使います。変換後もCR・LF・NULなど現在のコマンド引数制約を維持します。

[sftp-client.cpp](../../../elder-terms-terminal/src/sftp/sftp-client.cpp)は、libsshの`attributes->name`と正規パスをそのまま保存・表示・送信します。使用環境のlibsshは0.10.6で、[公開API](https://api.libssh.org/stable/group__libssh__sftp.html)のSFTP版は3です。[v3に対応するドラフトの6.2節](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-6.2)ではUTF-8を必須としておらず、[libssh 0.10.6の実装](https://github.com/libssh/libssh-mirror/blob/libssh-0.10.6/src/sftp.c)でも名前を送受信する際の文字コード変換はありません。「SFTPなら常にUTF-8」とする前提は置けません。

SFTPのファイル名用設定も既定値をUTF-8とします。SSH端末の`encoding`から自動継承せず、REALPATH、READDIR、OPEN、名前変更、削除、リンクを含め、元のパスと表示を分離します。対象サーバーの例として、[OpenSSHのREADDIR実装](https://github.com/openssh/openssh-portable/blob/V_9_6_P1/sftp-server.c)はファイルシステムから得た名前をそのまま返します。

### SMBとURLを扱う方式の違い

SMB v2/v3の文字列は[MS-SMB2の規定](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/6eaf6e75-9c23-4eda-be99-c9223c60b181)でUTF-16です。[libsmb2の名前変換](../../../deps/libsmb2/lib/unicode.c)とCREATE・QUERY_DIRECTORYの呼び出しを確認しました。サーバーのローカルファイルシステムが使う文字コードを、アプリから同じ設定で指定する仕組みではありません。SMB v1のロケール依存とUnicodeの範囲はplan18へ追記します。

WebDAVは[URLの扱い](https://www.rfc-editor.org/rfc/rfc4918.html#section-8.3)と[XMLの文字コード](https://www.rfc-editor.org/rfc/rfc4918.html#section-19)が別の契約です。XMLがUTF-8でも、hrefのパーセント表記の内容までUTF-8とは限りません。現在の[webdav-url.cpp](../../../elder-terms-terminal/src/webdav/webdav-url.cpp)はパスを復号してUTF-8検証し、その文字列からURLを再生成します。非UTF-8のパスを扱うなら、この部分を変え、既存hrefを表示文字列から作り直さないことが必要です。

WebDAVの互換設定を追加する場合は、URLパスの表示と新規名からURLを作るための文字コードとして定義し、既定値をUTF-8とします。PROPFINDのXMLやファイル本文へ一律に適用せず、既存hrefのバイト列を変更しません。HTTP/HTTPSの簡易クローラでは、元のURLを保持する設計をplan16へ補足します。

### 共通部分の変更と試験の境界

全方式で、表示名と操作対象を識別するパス・URLを分けることが前提です。現在の[file-transfer-engine.cpp](../../../elder-terms-terminal/src/file-transfer/file-transfer-engine.cpp)には、取得済みの`child.path`を使わず、親と`child.name`を連結する再帰探索・削除があります。NFS対応時にはこれを直し、新規の子の生成も各クライアントの変換境界へ渡します。UTF-8へ復号できない名前や、同じ表示名になる別の名前を識別できる契約が必要です。

変換不能な名前、CP932の途中の`0x5c`、Unicodeの合成形・分解形（NFC/NFD）、`%`・`?`・`#`、混在符号化、ローカル保存名の衝突を試験対象にします。既存項目への要求で元のバイト列が維持されること、新規名の変換不能時にリモートを変更しないことを確認します。ファイル本文、端末表示、認証情報の変換はこの設定へ混在させません。

文字コード設定を追加する各方式で、どの設定層にも指定がない場合にUTF-8になることを確認します。OSのロケールや端末通信の設定を変えても既定値が変わらないこと、明示値の継承・上書き・解除が働くことも検証します。

NFSに必要な共通契約はplan17の段階1・2で扱います。FTP/FTPS・SFTPの設定追加とWebDAVの互換対応は追加の実装計画へ分ける対象とし、plan15のジョブ・アイコンの実装へ混在させません。今回の調査では、必要な変更箇所と適用要否を記録します。

## 全計画に共通する実施条件

各段階は、動作を観測できるドライバーまたは画面まで作ってからコミットします。変更前に要求を再現するテストを追加してREDを確認し、実装後にGREENを確認する手順です。機能削除を伴う場合は、削除を検証するテストでRED・GREENを確認して一度コミットし、そのテスト自体も削除して整理します。

ビルドと全体テストの入口は、既存の`make build`と`make test`です。各planの実装完了時には全体テストを実行し、条件付き試験の未実施と成功を区別して記録します。ただし本planの実施では、利用者の指示に従いplan15の関連テストだけを実行します。ビルド警告は原因を調べて解消します。計画書を作成した時点では、文書の整合性と参照先を確認し、製品のビルドやテストは行っていませんでした。

GTKの試験には既存のC++ドライバーとVitest・gestamentを使用します。時間に沿った挙動は動画を撮影し、状態変化をアサートします。期待画像の追加・変更時は目視で確認し、画像や動画に表示崩れがあれば原因を調査して修正します。

外部APIは採用する版の公式文書と公開ヘッダーのコメントを照合します。既存のサブモジュール参照や外部コードは変更しません。新しい依存の追加は原本を固定して行い、修正パッチを当てない方針です。公開APIが不足する場合は、必要な契約と再現ドライバーを成果物とし、内部APIへの依存で代替しません。

実装の作業ブランチは、issueがあれば`feature/<issue番号>`、なければ内容を表す名前にします。本planなら`feature/transfer-jobs-and-icons`です。各段階で`feat:`、`fix:`、`refactor:`、`chore:`、`doc:`の適切なコミットを作り、mainへのマージは含めません。利用者向け文書は日本語を原本として更新し、英語版へ反映します。計画書へのリンクは一般文書へ追加しません。

## ツリーノードの表示

左右のローカル・リモートツリーで、名前の前に同じ寸法のアイコンを置きます。展開矢印の操作領域、行高、複数選択、ドラッグ開始位置は既存の操作を保ちます。初期寸法の候補は16論理ピクセルです。表示倍率に合わせた描画も検証します。

| 分類 | 既存Material資産の候補 | 判定例 |
| --- | --- | --- |
| ディレクトリ | `file/folder` | 通常のディレクトリ |
| SMB共有 | `file/folder_shared` | SMBクライアントが共有ルートと通知した項目 |
| NFS公開ルート | `device/storage` | plan17が公開ルートと通知した項目 |
| 一般ファイル | `editor/insert_drive_file` | 未知の拡張子、拡張子なし |
| 文書・PDF | `action/description`、`image/picture_as_pdf` | `.txt`、`.md`、`.pdf` |
| ソースコード | `action/code` | `.c`、`.h`、`.cpp`、`.ts`、`.json`など |
| 画像・音声・動画 | `image/image`、`image/audiotrack`、`av/movie` | `.png`、`.jpg`、`.mp3`、`.wav`、`.mp4`など |
| 圧縮ファイル | `content/archive` | `.zip`、`.tar`、`.tar.gz`、`.7z`など |
| シンボリックリンク | `content/link` | リンク自身の種別。リンク先は追加取得しない |

拡張子は大文字・小文字を同じ扱いにし、複合拡張子は長い一致を優先します。未知の項目も必ず一般アイコンで表示します。アイコンのために内容の読み込みやネットワーク通信は行いません。

共有やexportsは、パスの深さだけでは通常フォルダーと区別できません。`RemoteFileAttributes`へ表示上の役割を追加し、種別はディレクトリのまま保ちます。役割は表示用であり、変更可否は引き続き`path_capabilities()`で判断します。Material資産は元ファイルを編集せず利用する方針です。通常行・選択行・暗い背景のすべてで輪郭が見える色を選びます。

## 転送ジョブの単位と責任

ジョブは「利用者が一度に指示した転送」を表します。複数ファイルやディレクトリを選んでも一つのジョブとし、内部の項目数と進捗を表示します。プロトコルのクライアント、ジョブの状態管理、画面表示を分け、共通モデルにGTKウインドウへの生ポインターを持たせません。

ジョブにはID、接続の識別子と世代、方式、方向、転送元・先、開始・終了時刻、進捗、結果、キャンセル手段を持たせます。IDは再接続後も古い通知と区別できる値です。認証情報は表示用データや履歴に含めません。

| 状態 | 表示と操作 |
| --- | --- |
| 待機 | 接続の実行枠を待つ。取り消し可能 |
| 調査中 | 再帰探索中。件数・総サイズが未確定であることを表示 |
| 転送中 | 確定済みの総量があれば割合を表示。不明なら転送済みバイト数と件数を表示 |
| 判断待ち | 上書き、スキップ、失敗後の再試行などの入力を待つ |
| 中止処理中 | 通信と一時ファイルの後始末を待つ。後始末の終了まで「中止済み」にしない |
| 完了・失敗・中止済み | 成功数、スキップ数、失敗箇所、未処理数、残った一時ファイルを結果として保持 |

最初は現在の一接続一転送を維持します。キューを追加する段階で、待機ジョブの条件を実行直前に再確認します。再試行は失敗した操作の再試行と、終わったジョブを新しいIDでやり直す操作を区別し、転送途中からの再開は保証しません。

総バイト数が不明なHTTP受信や探索中のディレクトリでも、0%や100%を誤表示しない契約にします。現在のエンジンの戻り値は`void`なので、全項目スキップを無条件の成功件数に含めないよう、終了結果の集計も追加します。

## ジョブ一覧の配置と採用案

案Aを採用します。比較した案は下表に残しますが、今回の実装対象はAだけです。

| 案 | 配置と操作 | 利点 | 制約 |
| --- | --- | --- | --- |
| A・採用 | 転送画面の下部に高さを変えられる折り畳み一覧。閉じていても件数と進捗の要約を残す | 左右のツリーと転送先を見ながら経過を追える。既存の単独ウインドウに収まる | 小さい画面ではツリーの高さが減る |
| B | 画面右側の開閉パネル | 行ごとにエラーや操作を置きやすい | 左右ツリーの横幅が減り、長いパスが読みにくくなる |
| C | 独立したジョブウインドウ | 多数のジョブを広い画面で確認できる | 全接続を集約するなら別プロセス間の通信と寿命管理が必要 |
| D | ヘッダーの進捗ボタンから開くポップオーバー | 普段のツリー面積を保てる | 長時間の監視と多数の失敗の確認には向かない |

A案の初期表示は、方向、対象名、状態、進捗、中止ボタンをまとめた一行です。選択した行を展開すると転送先と結果の詳細を確認できます。実行・判断待ち・失敗の行を優先し、終了済みの履歴は手動で消せる構成です。履歴はそのプロセスの実行中だけ保持し、再起動後のジョブ復元は今回の対象に含めません。

所有単位は転送ウインドウです。そのウインドウのFTP、FTPS、SFTP、WebDAV、SMBなどのジョブを一覧に表示します。端末ウインドウへの一覧追加や、X/Y/ZMODEM・テキスト送信との統合は行いません。

画面の折り畳みではジョブを継続します。所有ウインドウを閉じると待機ジョブを取り消し、実行中の処理と後始末を終了させてから接続を破棄する方針です。ブラウザー操作を転送中も許す段階では、読み取り要求を接続側で直列化し、同じ転送先への削除や名前変更を禁止します。

## 段階1：既存ツリーへアイコンを表示する

通常フォルダー、ファイル分類、SMB共有の表示を先に完成させます。役割の型にはNFS公開ルートも含めます。NFSの通信実装はplan17の対象です。

テストでは、名前・種類と見た目の対応、選択後も読める表示、展開矢印、クリック・複数選択の機能を確認します。SVGの存在確認だけを合格条件にしません。成果物は既存SFTP・SMBを実際に操作できる転送画面です。完了条件は、通常項目と共有ルートを見分けられ、転送とツリーの操作が通ることです。

## 段階2：現在の一件の転送をジョブで動かす

既存の進捗オーバーレイを表示先として残し、実行、キャンセル、判断待ち、終了結果をジョブから通知する構成に置き換えます。単一転送の動作を観測できるC++ドライバーと既存GUIテストで、状態の順序、例外、ウインドウ破棄、二重終了を検証します。

この段階では同時実行を増やしません。完了条件は、現在の操作でジョブが一つ作られ、成功・スキップ・失敗・中止が正しく集計されることです。

## 段階3：画面下部の一覧を表示し、待機キューを加える

案Aのジョブ一覧と折り畳み時の要約を、転送画面の下部へ統合します。既存のオーバーレイを置き換え、判断待ちの入力も操作できる構成にします。その後で同じ接続への追加転送をキューに入れます。

一覧で中止したジョブだけが止まること、探索中にも中止できること、判断待ちで後続処理が割り込まないことを確認します。切断後の待機ジョブは自動実行せず、再接続後の再試行対象として明示します。完了条件は、二つ以上のジョブを順に実行し、画面を操作しながら状態と結果を追えることです。
