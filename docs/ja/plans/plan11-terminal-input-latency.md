# plan11：使用継続に伴うターミナル入力遅延の調査

作成日：2026年10月27日

状態：2026年10月29日、boxrig 0.9.0への依存更新と、このPCでの更新前後の比較を終えました。Codex型模擬負荷では、入力応答の中央値が約1.1〜1.3秒から63〜66msへ短縮しています。その後、developの修正版を取り込み、保留していた行単位の装飾削除、矩形選択、SSH試験の後片付けを修正しました。「リンクをコピー」も追加し、各再現試験とルートの全体試験が成功しています。実際のCodexセッションとの直接照合は残っています。末尾の追加対応より前の試験結果は、0.9.0更新直後の記録です。

実施条件の更新：2026年10月27日、利用者から、このPC上で実施するよう指定がありました。症状はLocal terminalとSSHの両方で発生しています。接続方式への非依存性は未確認です。段階5の比較もこのPC内で行い、別PCでの測定は今回の範囲から外します。

利用プログラムの追記：普段の利用条件はCodex CLIです。このPCで確認した版は0.164.0で、`fullscreen_transcript=false`でした。単純な追記との違いを調べるため、端末の一部をスクロールして履歴へ送り、入力欄を書き換える負荷を段階2に追加します。同期更新で描画をまとめる条件と、可視リンクにポインターを置く条件も比較します。Codex側の動作は[同版の履歴挿入処理](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/insert_history.rs)と[端末更新処理](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/tui.rs)を参照します。これらの負荷はCodexの出力方式に着目した模擬試験で、Codexそのものを実行した結果とは区別します。

## 症状と調査の目的

elder-termsのターミナルを使い続けると、徐々に反応が遅くなるとの報告があります。悪い場合には、1文字を入力してから応答まで2〜3秒かかります。スクロールバッファのデータ量に比例しているようにも感じられるものの、その関係は未確認です。別のPCでも同様に遅くなり、複数の接続方式で発生しています。

この計画では、画面外へ流れた過去の本文をスクロールして参照できる領域を「履歴」と呼びます。設定した履歴の上限と、実際に保持している履歴行数は区別します。

まず、履歴量に応じて1回の処理が重くなるのか、未処理の仕事が溜まって入力を処理する順番が来ないのかを切り分けます。そのうえで、elder-termsと端末ライブラリのboxrigのどの処理に原因があるかを特定します。複数のPC・接続方式で発生するため、通信方式固有の処理より、共通の入力処理・端末モデル・描画を優先します。

対象は原因特定と、その根拠を再現できる試験・測定結果です。原因を確認した後の製品修正は、調査結果に基づいて別途具体化します。

## 調査開始時のコードと候補

計画立案時に確認したelder-termsは`73c47b86fa699d1cabed0d0117e458911390b4b5`です。boxrigは0.8.0の`2576a9169fb4ac18f93fd28442a8067b2ba2dcbd`を参照しています。測定を始める際には、実際に使用するソースとバイナリの参照を改めて記録します。

### 入力処理より前に実行される仕事

elder-termsの`dispatch_frame()`では、リンク認識とモデル同期の後に、端末表示部品のフレーム処理を実行します。boxrigはそのフレーム処理でキューに入ったキー入力を処理するため、前段の仕事が長ければ入力も待たされます。

確認箇所は[terminal-runtime.cpp](../../../elder-terms-terminal/src/terminal-runtime.cpp)の`dispatch_frame()`と、boxrigの[GTKフレーム処理](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/gtk3/terminal_widget.c#L3369)です。

### リンク認識の準備で履歴を含む本文を走査する処理

boxrigのリンク認識には、本文や配置の変更に応じて認識の準備をやり直す処理があります。その準備で呼ぶ`boxrig_screen_text_document_size()`は、履歴を含む本文の全論理行を走査します。論理行は、画面幅によって折り返された表示行をつなげた本文の行です。

この準備は、認識処理に作業量の上限を渡す前に実行されます。elder-termsが指定する4,096単位の作業量だけでは、準備を含む呼び出し時間の上限を判断できません。

確認箇所はboxrigの[認識続行処理](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/core/recognizer.c#L1620)、[認識準備](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/core/recognizer.c#L514)、[本文全体の行数・サイズ計算](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/core/text.c#L1377)です。

### 履歴行の削除通知による認識器の再登録

elder-termsは`LINE_EVICTED`という行の削除通知を受けると、該当するリンク認識器を解除し、再登録します。その際にリンクの注釈も消去します。履歴上限に達した後、再登録と再認識が繰り返されていないかを確認します。

確認箇所は[terminal-links.cpp](../../../elder-terms-terminal/src/terminal-links.cpp)の`terminal_links_dispatch()`と`restart_recognizer()`です。再登録先のboxrigでも[登録処理から認識準備を呼び出します](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/core/recognizer.c#L1528)。

これらはコード上の候補です。現時点では、2〜3秒の遅延を説明できるか、実際の利用中にどれだけ実行されるかは未測定です。履歴量との相関だけで原因を断定せず、区間別の時間と比較試験で確かめます。

## 段階1：1文字の入力遅延を再現・計測する

ローカルPTYに、1文字を受け取るたび識別可能な応答を返す試験用プログラムを接続します。PTYは、ローカルのプログラムとターミナルの入出力をつなぐ疑似端末です。シェルの補完やプロンプト処理に左右されず、通常のキー入力経路を通して計測できる試験にします。

測定点は、キー送出、GTKでの受信、相手プログラムでの受信、応答の端末側での受信、本文解析完了、描画提出、画面への反映です。入力・応答・表示を対応付け、どの区間で待っているかを記録します。

描画提出と実際の表示は別の終点として扱います。表示は時刻付きの動画・画素観測で確認し、表示された応答とログの対応を検証します。画面キャプチャでの観測時刻を、物理モニターの走査完了時刻とは見なしません。

最初は新しい端末で基準値を取ります。実行バイナリ、設定、画面サイズ、フォント、描画方式を固定し、PCと表示環境も記録します。利用中の端末と専用の測定用プロセスを区別します。

成果物は、実行できる1文字応答の試験と、入力ごとの区間別時刻・基準値の記録です。完了条件は、1文字ごとの遅延を区間別に記録でき、入力・応答・表示の対応を確認できることとします。

## 段階2：履歴量・累積出力量・経過時間を分ける

段階1の試験に、履歴の追加や画面更新を繰り返す条件を加えます。最初からすべての組み合わせを試すのではなく、次の比較で悪化する条件を絞ります。

| 比較条件 | 判別したいこと |
| --- | --- |
| 実際の保持履歴を0、1千、5千、1万行と増やす | 履歴量に応じて遅くなるか |
| 履歴上限に達した後も出力を続ける | 古い行の削除が契機か、保持量が一定でも悪化するか |
| 履歴を増やさず同じ画面を繰り返し更新する | 累積更新回数に依存するか |
| 同じ時間、無出力で待つ | 時間経過だけで悪化するか |
| 大量出力中と、出力停止・処理完了後に入力する | 一時的な処理待ちか、残り続ける劣化か |

各時点で、入力遅延の中央値・p95・最大値、CPU使用量、メモリー使用量、未処理データ量を記録します。p95は、測定した遅延の95%がその値以下になる境界です。経過時間、累積出力量、実際の保持履歴行数も対応付けます。

現在の履歴上限の既定値は1万行です。0行の条件は、新しい端末など、実際の保持履歴が空の状態を指します。上限設定を0にする意味ではありません。設定値と実際の保持行数を混同せず、上限到達前と、古い行を捨て始めた後を比較します。

悪化する条件が見つかったら、URLを含む行、普通の短い行、長い折り返し行を比較します。履歴を明示的に破棄した場合や、端末を再作成した場合に回復するかも確認します。回復したという結果だけで原因を決めず、次の区間計測と照合します。

各条件は複数回実行し、比較順序を入れ替えます。出力停止後の試験では、未処理の仕事が残った状態と処理完了後を区別します。想定以上に時間がかかる場合は、単に待機上限を伸ばす前に、処理が進んでいるかを調べます。

成果物は、同じ端末を使い続けたときの時系列の測定結果と、悪化・回復条件の比較表です。完了条件は、何を増やすと悪化し、何をすると回復するかを繰り返し再現できることとします。

## 段階3：遅い区間を処理時間と待ち時間に分解する

段階2で再現した条件に絞り、詳細な計測を追加します。リンク認識の準備・続行、認識器の再登録、モデル同期、フレーム処理、GTKと描画側の待ちを個別に測ります。

履歴行の削除件数、認識器の再登録回数、走査量、保留イベント数も記録します。1回の全体走査が長いのか、短い処理が大量に繰り返されるのかを区別するためです。再登録は呼び出し回数と1回の所要時間を両方測り、履歴上限到達との関係を確認します。

実時間とCPU時間を比べ、CPU時間が短いのに実時間だけ長い区間では、I/Oや描画同期などの待ちを追います。入力遅延と同じ時間帯の処理を調べ、累積CPU時間だけを見て原因とは判断しません。

計測自体で遅くしないよう、本文全体の取得や毎イベントの同期ログ出力を避けます。詳細な計測を加えた試行と、軽い計測の試行を比較し、遅延の傾向が変わっていないかを確かめます。

成果物は、長い入力遅延と、その間に実行・待機していた処理を対応付けた記録です。完了条件は、観測した長い入力遅延の主要部分を、具体的な処理または待ちで説明できることとします。

## 段階4：同じ再現条件でelder-termsとboxrigを比較する

同じ出力・履歴量・設定で、次の順に構成を小さくします。それぞれを実行して、遅延が残るかを観測します。

| 比較する構成 | 遅延が残る範囲から次に調べる対象 |
| --- | --- |
| elder-terms本体 | 本体だけで遅ければ、周辺UIや設定連携 |
| elder-termsの共通端末処理を載せた最小ドライバー | スケジューリング、リンク認識の呼び方、共通の入出力処理 |
| boxrigのGTKサンプル | boxrigの端末表示部品、端末モデル、GTKとの連携 |
| 描画を伴わないboxrigコア | 本文の更新、履歴管理、リンク認識などのコア処理 |

比較時には、リンク認識、アクセシビリティ、描画方式と処理完了条件をそろえます。アクセシビリティは、支援機能や自動操作などへ端末本文を公開する仕組みです。リンク認識が未完了の構成と、最後まで処理した構成の速度を、そのまま比べないようにします。

既存の[boxrig-driver.cpp](../../../elder-terms-terminal/src/boxrig-driver.cpp)には、本文取得などの観測処理があります。その処理の影響を含んだ速度差を、製品の差とは扱いません。最小構成でも、必要な機能と計測による追加負荷を確認します。

リンク認識の有無、描画方式のOpenGLとCairoの比較も、段階3で疑わしかった区間に応じて一要因ずつ行います。複数の機能を同時に変えて原因を判断する方法は採りません。

成果物は、遅延が残る最小構成と、同じ条件で問題が消える対照構成です。完了条件は、両者を実行して比較でき、elder-termsの呼び方、boxrig内部、描画環境のどこをさらに調べるべきかを説明できることとします。

## 段階5：実際の利用条件で照合し、原因特定を締める

最小構成で得た説明を、このPC上のLocal terminalと検証用SSH接続で照合します。ローカルで再現しない場合は、同じ区間計測をSSH接続へ適用します。接続方式ごとの違いは、共通処理の結果と分けて記録します。

最終成果物は、再現手順、時系列の測定結果、遅延区間、原因候補を支持・否定する比較結果です。徐々に悪化する仕組みと、観測した長い待ちを説明できることを完了条件にします。速度が少し改善しただけでは、原因特定を完了したとは判断しません。

再現しない場合は、未再現の条件と、次回発生時に採取する情報を明確に残します。その場合は調査記録の整理までを行い、原因特定は未完了として扱います。

## 実装・検証・記録の進め方

最初に着手するのは段階1と段階2です。特に、1万行の上限到達前後と、出力停止後の1文字入力を比較します。その結果を使って、段階3以降の計測対象を絞ります。

各段階では実行可能な試験と観測結果を残します。調査用コードを追加・変更する場合も、問題を再現する試験でREDを確認してから実装し、GREENを確認します。機能の検証は実際の入出力や完了状態を使い、PCの速度だけに依存する固定時間の判定に寄せません。性能値の比較と機能の正しさは分けて評価します。

画面への反映を検証する試験では動画を記録し、応答の順序と到達を確認します。期待画像を追加・変更する場合は、画像を目視してから採用します。待機上限に達した試行や測定に失敗した試行は、成功した遅延値へ混ぜず記録します。

調査用コードを変更した場合は、段階ごとの対象試験に加え、作業完了時に全体テストを実行します。ビルド警告と試験の失敗は分析し、測定対象の問題と環境による制約を区別します。計画書だけの保存では、ビルドや全体テストは不要です。

外部ライブラリAPIを使う実装では、公式ドキュメントとAPIコメントの両方を確認します。`deps/boxrig`などの外部コードは直接変更せず、診断用ドライバーや計測コードはelder-terms側で管理します。段階ごとの成果物は`chore:`、調査結果の記録は`doc:`など、内容に合った単位でコミットします。mainへのマージは行いません。

## 実施記録

### 段階1の計測基盤

現行コードを`npm run build`でビルドし、コンパイラ警告なしで完了しました。計測用のプログラムは[tests/performance](../../../elder-terms-terminal/tests/performance/)へ追加しています。製品の入力・通信・描画処理は変更していません。

`latency-peer`はraw PTYで1文字を受け取り、連番に対応する背景色と端末タイトルを出力します。キーの受信・応答書き込み時刻、累積出力量を記録します。`latency-input`はXTestでキーを送出し、ウィンドウ画素に対応色が現れるまでを測定します。履歴量、plain・URL・折り返しの本文、追記・同じ画面の上書き・無出力を選べます。

`latency-probe.so`は公開関数の呼び出しを観測します。GTKへのキー配送、PTYでの応答受信、本文解析、認識処理、モデル同期、フレーム処理、draw、GTK/GDKへの描画提出を記録します。レコードは上限付きのメモリー領域に保持し、終了時に出力するため、各イベントでログファイルへの同期書き込みは行いません。記録上限を超えた試行は集計時に失敗とします。

GTKのイベント受信は、[イベント処理の公式説明](https://docs.gtk.org/gtk3/input-handling.html)と[GdkEventFunc](https://docs.gtk.org/gdk3/callback.EventFunc.html)、インストール済みヘッダのAPIコメントを確認しました。描画提出の終点には[公開end_draw_frame API](https://docs.gtk.org/gdk3/method.Window.end_draw_frame.html)を使っています。関数の観測は[dlsymのRTLD_NEXT](https://man7.org/linux/man-pages/man3/dlsym.3.html)を使い、本来の関数へ引数・返り値を渡します。

PTY応答がまだ存在しない状態でREDを確認した後、実装してGREENを確認しました。計測器も既存の端末動作試験に対して、ログが取得できないREDと取得できるGREENを確認しています。実際のXTest入力では最初の観測方法でGTK時刻を取れなかったため、区間の欠落を検出する試験を追加しました。GDKのイベント配送を観測する方法に変更し、全区間が対応することを確認しています。

`npm run test:latency --workspace=elder-terms-terminal`で、PTYプロトコル、Xvfb上のキー入力、マーカー領域とウィンドウ全体の録画、実アプリの区間計測を確認できます。録画はFFV1をRGBへ復号し、各フレームの色とログ、応答の出現順を検証します。TypeScriptの型検査も成功しました。

区間の集計では、空のログ、時刻の逆転、別ウィンドウの描画提出、画素観測後の提出を受け入れない試験を追加し、REDからGREENを確認しました。GTKのdrawシグナルは画面への転送を含む区間であり、描画全体の時間とは区別します。Cairoの主要な描画はframe内で行われるため、frameの所要時間も別に残します。実際に選ばれた描画方式も公開APIから記録します。

drawとの対応付けには、応答解析後の連番・本文revision・時刻・描画ウィンドウを使います。これはGTKの観測区間の対応であり、非同期描画の各画像に応答が含まれることまで保証するものではありません。表示到達の判定は連番に対応した画素の初見を使い、原因の判断にはCPUプロファイルと対照試験も合わせます。

量的な比較には録画方式の引数へ`none`を指定し、画素観測だけを行います。`video`ではマーカー領域、`full`ではウィンドウ全体を録画します。その次の引数は接続方式で、`local`または`ssh`です。計測を外す`off`でも同じjemallocを読み込み、メモリー割り当て方式をそろえます。画面設定は環境変数`ELDER_LATENCY_COLUMNS`、`ELDER_LATENCY_ROWS`、`ELDER_LATENCY_FONT`で変更でき、実行条件に記録されます。

### リンクの装飾に関するコード上の根拠

リンクの下線や色を本文位置へ対応付けた情報を、boxrigではtext annotationと呼びます。モデル同期は本文のrevisionが変わると全annotationを処理し、それぞれについて可視行を調べます。その内側に、履歴を含む行情報を先頭から探す処理があります。annotation数をA、可視行数をR、履歴を含む行数をHとすると、A×R×Hに応じて増える走査を含みます。

参照箇所はboxrigの[モデル同期](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/ui/view.c#L2414)、[annotationの更新範囲の計算](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/ui/view.c#L1573)、[履歴からの行探索](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/ui/view.c#L968)です。[描画用のannotation問い合わせ](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/ui/view.c#L4209)にも同じ探索があり、[Cairo](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/pangocairo/renderer.c#L2690)と[OpenGL](https://github.com/kekyo/boxrig/blob/2576a9169fb4ac18f93fd28442a8067b2ba2dcbd/src/opengl/renderer.c#L765)の両方が利用します。

責任範囲を確かめる最小試験として`annotation-cost`を追加しました。GTK、通信、正規表現認識、描画を使わず、boxrigの公開APIだけで履歴とannotationを保持します。1文字相当の本文更新、モデル同期、可視行のannotation問い合わせを別々に測ります。試験では、入力後も保持履歴が変わらず、見えるannotationが有効なままであることを確認しています。これはboxrig UI層の切り分けであり、UI層を使わないcoreの本文解析も同じ原因で遅いとする試験ではありません。

### このPC内のSSH照合と未確認事項

SSHは専用の一時鍵と設定を用意し、127.0.0.1の空きポートで検証用サーバーを起動しました。普段の接続設定は変更していません。履歴1万行を準備した無出力状態で12キーを測ると、リンク表示有効の中央値は485.666ms、無効は57.485msでした。Local terminalの結果と同じ傾向です。

SSHのこの比較は区間計測を外しており、保持履歴や実際に選ばれた描画方式を直接観測していません。1万行・OpenGLを指定した比較として扱います。Localの詳細・軽量計測では、実際の描画方式がOpenGLであることを確認済みです。

SSHで10msごとに8行を追加し続ける試行では、2キー目の画面反映を10秒以内に観測できず失敗しました。これは成功した遅延値に混ぜていません。出力の滞留や通信側の待ちを区間別に確認できていないため、この10秒超を同じ原因だけで説明したとは扱いません。失敗時の画素観測は`artifacts/plan11/transcript-ssh-on/`に残しています。

現時点で確認したのは、報告された規模の遅延を生むboxrig UIの処理と、その最小再現条件です。ユーザーの実際のCodexセッションで、遅くなった瞬間と同じ関数が対応するかは未確認です。既定ルールは本文中のHTTP・HTTPS URLを認識します。OSC 8だけで与えられるファイルリンクや、URLを含まない長時間利用が同じ原因になるとは断定しません。ポインターをリンク上へ置く条件の比較も未実施です。

次に実利用で遅くなったときは、本文を採取せず、該当端末のCPUプロファイル、保持履歴、リンク認識と描画の区間を対応付けます。今回の行探索が支配的でなければ、この結論をそのセッションへ適用せず、残る待ちや別の更新経路を調べます。現在の原因特定を根拠に、製品修正まで完了したとは扱いません。

履歴1万行のすべてにURLを置く条件は、両版とも既定設定では認識を完了できませんでした。boxrigの[既定値](https://github.com/kekyo/boxrig/blob/2f57cee10fe1e7ebdf920dbb61c98f6d15c0e1af/src/core/recognizer.c#L396)では`dirty_line_capacity`が8,192で、今回の一致行数がこの上限を超えます。補助試験の未完了12試行は性能比較から除外し、生データの`failures`に残しています。実アプリの高密度試行でも、両版に認識未完了の通知が33回ずつありました。この条件で入力応答が短くなった値を、リンク処理の改善根拠には使いません。

処理量への依存を調べる補助条件として、両版ともこの上限を16,384、イベント容量を32,768に広げました。この場合は、100行追加時のCPU時間が82.65秒から115.74msへ減り、両版とも正しいリンク結果まで完了しています。これは製品の既定設定とは異なる測定です。製品コードやboxrigのソース、認識上限は変更していません。

### リンクコピー追加によるホバー解決への影響

既存の`osc8-resolve-cost.cpp`を変更せず、旧・新のリンク処理を同じSDKへリンクして比較しました。CPU0に固定し、各版6プロセス、実行順序を反転しています。次の値は、キャッシュに結果がある状態で1回の解決にかかる時間です。各プロセス内の2試行を平均し、6プロセスの中央値を求めました。

| 一致するURIの長さ | 修正前 | 修正後 | 増加量 |
| --- | --- | --- | --- |
| 64バイト | 0.726µs | 0.741µs | 0.015µs |
| 512バイト | 0.779µs | 0.795µs | 0.016µs |
| 8,192バイト | 1.928µs | 1.935µs | 0.007µs |

不一致URIのキャッシュ利用も含め、増加量は約1〜16nsでした。キャッシュへの登録後に測った試行1・2では、正規表現マッチャーの作成とキャッシュ追い出しは0回です。わずかな増加はありますが、この測定では大きな負担は確認できませんでした。これはホバー解決の比較で、右クリック操作やクリップボードへのコピー時間の測定ではありません。[集計](../../../artifacts/followup-performance/hover-summary.json)と[生データ](../../../artifacts/followup-performance/hover-raw.tsv)を保存しました。生データのtrial 0は初回問い合わせ後の反復も含むため、単独のキャッシュ未登録時の所要時間としては扱いません。

### 評価結果と再現方法

今回の追加修正は、履歴上限に達してリンク付きの行が消える場面で、再認識の仕事を減らす効果があります。固定量の補助試験では差が明確で、実アプリの登録回数と認識CPU時間にも対応する変化がありました。一方、画面応答は短縮と増加が混在しています。追加修正によって体感速度も一段上がったとは、今回の測定からは結論できません。

測定順序、条件、各試行の値を保存し、入力・録画・認識結果を確認できたため、今回の性能評価の完了条件を満たしました。件数と測定器のソース・バイナリのハッシュは[評価記録](../../../artifacts/followup-performance/evaluation.json)にまとめています。製品コードは変更していません。全体テストは前節に記録した同じ製品コードの成功結果を用い、測定器の意味検証と録画照合を追加しています。実際のCodexセッションとの直接照合は未実施です。

再現用の[GUI測定](../../../artifacts/followup-performance/run-gui.mjs)、[区間計測なしのGUI測定](../../../artifacts/followup-performance/run-gui-untraced.mjs)、[補助試験のMakefile](../../../artifacts/followup-performance/Makefile)、[反復実行](../../../artifacts/followup-performance/run.mjs)、[ホバー測定](../../../artifacts/followup-performance/run-hover.mjs)を保存しました。GUI測定は、既存の結果を保存したまま出力先を別名へ変更し、`xvfb-run -a --server-args='-screen 0 3840x2160x24' node <測定スクリプト>`で起動します。補助試験は同ディレクトリで`make`を実行後、`node run.mjs --cpu=0 --order=old-new --iterations=100 --repeats=3`と、`--order=new-old`に替えたコマンドで実行できます。出力先と上限条件を変更する引数も用意しました。
