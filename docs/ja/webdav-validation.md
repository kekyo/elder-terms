## 独立したApacheでの検証

39ケースはHTTPの7ケースとHTTPSの32ケースから成る。認証なし、Basic、Digest、自動選択、不正パスワードの拒否、TLS 1.2/1.3、独自CA、未信頼証明書の拒否、明示的な許可、システムCAを含む。成功ケースでは40 MiB + 13バイトの規則的な内容、空ファイル、Unicodeと特殊文字を含む名前、入れ子の空フォルダーを転送し、上書き、衝突時の保持、名前変更、削除を検証する。サーバーの記録でPROPFIND、GET、PUT、MKCOL、MOVE、DELETEと実際のTLSバージョンを確認する。

ランナーはMesonの全体テストに登録されている。Apache、その認証ユーティリティー、証明書ツールをインストールした使い捨て検証コンテナーまたは識別済みゲストでのみ有効化する。

```sh
ELDER_TERMS_TEST_APACHE_WEBDAV=1 meson test -C .build --no-rebuild --num-processes 4 --print-errorlogs
```

一時的なシステムCAの追加と除去は、その隔離環境内で行う。ホストのCAストアは書込み可能でマウントしない。独立したNode.js fixtureでは、部分応答・エラー応答、不正または安全でないXMLとパス、不明サイズ、圧縮応答、上限付きストリーミング、最終応答の消失、送信元サイズの変化、取消も検証する。HTTPの失敗や結果不明の変更操作を成功として扱わない。

## ソースとパッケージの一致

検証した15個のソースコピーは単一の固定アーカイブを使用し、最終実装と一致する。変更したMarkdown以外の全ファイルと、削除した実装ファイルが存在しないことを照合し、環境ごとのソース差分の例外は設けない。各パッケージは新規ビルドする。同じ対象の終了済みコンパイル出力をデバッグビルドに再利用する場合も、全体テストはすべて再実行する。各実行中のソースは固定した。

Ubuntu 26.04の回帰では、受信の一時停止を取り消した後にもlibcurlの停止状態が残る問題を検出した。次の要求が接続を取得した時点で、その要求のコールバックが指定した送受信の停止状態を適用するよう修正した。Digest認証を維持し、取消済みのコールバックは再配信しない。7.88.1では最終的な拒否応答の後にも送信の停止状態が残って完了を妨げたため、ソケット監視が不要になった段階で完了済みの送信方向を解放する。401の認証交渉は通常どおり維持する。全体回帰では受信・送信の一時停止中の取消、追加の入力を要求しない早期拒否、その後の同一セッションの再利用を確認した。[libcurlの公開pause API](https://curl.se/libcurl/c/curl_easy_pause.html)を使用する。修正前の全体失敗と、採用しなかった最初の修正候補の記録も保持する。

それ以前のインストール済み全体テストでは、ファイル操作成功後のパス入力のフォーカスで失敗した。[gestamentの公開API](https://github.com/kekyo/gestament/)に従い、ネイティブ入力前に対象ウィンドウをアクティブにする前提へ修正した。フォーカスの検査と実際のファイル操作の条件は維持する。また、以前の並行検証では、受信内容が一致していても既存TELNET/XMODEMの20秒の時間条件が失敗し、CPUの割当ての分離だけでは解消しなかった。最終の開発環境・配布版UIは、全配布ビルドと全ゲスト終了後に順番に実行する。ビルドはCPU 8〜23、最大2つのゲストはCPU 0〜7、その後のUIはCPU 0〜7を使う。配布マトリクスではUbuntu ARM64をコンパイル6並列、その他を4並列とした。インストール済みUI環境のパッケージ作成は2並列、デバッグビルドと全C++テストは4並列で実行した。最終の文書検査では、両言語の文書の完成によって、検証済みバイナリー、その他の内容、権限、シンボリックリンク、パッケージメタデータが変わらないことを確認した。

## 追加のメモリー診断

GCC 12のAddressSanitizer/UndefinedBehaviorSanitizerによる全C++の比較で、共通送信処理の開始時に使う一時的なキャンセル状態の寿命の問題を検出した。選択した通知と開始promiseを名前付き変数に保持する修正により、WebDAVとSFTP転送の診断は解消した。修正後の追加診断は126件成功、2件失敗、任意1件スキップだった。残る報告は未変更の既存IPスキャナーとSSH TCPリゾルバーにある。この既存診断は、成功した通常の配布・UIテストとは別に記録し、Sanitizerの全体成功とは扱わない。

診断コンテナーでは検査ランタイムの起動時の停止を避けるためアドレス配置を固定した。アプリケーションのビルドやホストのシステム設定は変更していない。関連する一時値の扱いは[GCCのコルーチンに関する説明](https://gcc.gnu.org/pipermail/gcc-bugs/2022-November/805094.html)も参照したが、今回の現象がその報告と同一とは断定しない。

## 検証環境の制約

インストール済みUIでは、描画を再現するための基準フォント、Yaruアイコン、専用の基準FreeTypeを使用する。アプリケーション、GTK、libcurl、OpenSSLは対象環境の版であり、パッケージと全C++は先に対象環境のライブラリーで検証する。[FTPSの検証記録](ftps-validation.md)と[基準FreeTypeのUbuntuパッケージ](https://packages.ubuntu.com/noble-updates/libfreetype6)を参照。

QEMUのユーザーエミュレーションは必要なio_uringの動作を提供しないため、異なるCPUの実行時検証にはシステムゲストを使用する。出典は[QEMU 8.2.2のLinux-userシステムコール処理](https://github.com/qemu/qemu/blob/v8.2.2/linux-user/syscall.c)。Ubuntu 26.04 arm64のビルドでは、[openat2の互換性問題](https://lists.gnu.org/r/bug-gnulib/2025-10/msg00108.html)のため、検証環境だけで旧版のtarを使用する。ARMv7は既存のrelease・`werror=false`設定でテストし、[GCC 12の文字列結合に対する警告](https://gcc.gnu.org/pipermail/gcc-bugs/2022-June/790598.html)も含めて警告を記録する。releaseは既存のGCCとベンダーのコルーチンのデバッグ情報生成エラーも回避する。詳細は[FTPSの検証記録](ftps-validation.md)を参照し、[該当ベンダーソース](https://github.com/kekyo/libxyzm/blob/caefbaf6727156fc2cc9fbc720a4e553848c7e3c/src/async/xyzm_ymodem.cpp#L1046)は変更していない。

i386の端末転送の試験相手には、従来のFTPS検証と同じく、未変更の[lrzszソース](https://github.com/UweOhse/lrzsz/blob/master/src/lrz.c)を[自動変数初期化](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-ftrivial-auto-var-init)付きで使用する。この試験相手は製品パッケージに含めない。2つのWebDAV C++ランナーは、古いNode.jsでも共有TypeScript fixtureを読めるよう、公開[TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API#a-simple-transform-function)でJavaScriptを生成してから読み込む。全3ワークスペースを対象とした別途のTypeScript型検査も成功した。
