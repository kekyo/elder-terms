# plan17：NFS v2・v3・v4のファイル転送

作成日：2026年11月2日

状態：段階1の検証ドライバーと共通転送の識別子修正を完了しました。各版の実通信と非同期停止を確認済みです。plan17本体は一時停止中で、追加指示のシステム版libnfsへの切り替えを反映しました。段階2以降の転送画面、送信・変更操作、設定統合、全体試験は未完了です。

## 目的と前提

libnfsを使い、NFSの公開ディレクトリを転送画面から閲覧・送受信できるようにします。exportは、サーバーが外部へ公開するディレクトリです。SMB共有と同様に、各exportをアプリ側のルート直下に置き、その中を通常のディレクトリとして操作します。

NFS v2はlibnfsの低水準RPC APIを使い、アプリ側で不足するファイル操作を補います。外部コードの編集や、NFS v2を実装せずにv3へ切り替える対応は行いません。古いプロトコルを使う判断とそのリスクは、依頼どおり利用者の責任であり、本planの対象外です。

調査基準と共通の実施条件は[plan15](plan15-transfer-jobs-and-tree-icons.md)を参照します。新しい接続種別として追加し、既存SMBの共有ブラウズを変更するための計画にはしません。

文字コードの設計は、指定された[共有議論「libnfsにおけるファイルパスの文字コードの扱い」](https://chatgpt.com/share/6ae83273-3b84-8323-8d00-145d1353f54a)を反映します。表示名と通信に使う元のバイト列を分離し、新しい名前を指定する境界で文字コードを変換します。共有議論のWindows向け例は設計の参考です。本プロジェクトではGTKのUTF-8表示と、使用済みの文字コード変換APIであるiconvに合わせます。

## 現在のコードと外部API

[RemoteFileClient](../../../elder-terms-terminal/src/file-transfer/remote-file-client.h)には、一覧、属性、読み書き、変更操作、能力情報が定義されています。[SMBのサーバークライアント](../../../elder-terms-terminal/src/smb/smb-client.cpp)はサーバールートと共有内パスを分け、共有ごとの接続を遅延して開始します。この責任分担をNFSでも使用します。

利用者の指定により、libnfsはシステムライブラリを使います。`pkg-config`で5.0.2以上の開発パッケージを検出し、サブモジュールへの追加や独自ビルドは行いません。検証環境はUbuntu 24.04で、`libnfs-dev`と`libnfs14`の版は`5.0.2-1ubuntu0.24.04.1`です。`pkg-config --modversion libnfs`では`5.0.2`を返します。

[5.0.2の公式README](https://github.com/sahlberg/libnfs/blob/libnfs-5.0.2/README)では高水準の同期・非同期APIとRAW RPC APIを区別しています。[公開ヘッダー](https://github.com/sahlberg/libnfs/blob/libnfs-5.0.2/include/nfsc/libnfs.h)と[RAW APIのコメント](https://github.com/sahlberg/libnfs/blob/libnfs-5.0.2/include/nfsc/libnfs-raw.h)を、実際の`/usr/include/nfsc/`と照合しました。

システム版5.0.2のRAW APIは`*_async()`で、要求を登録できると整数の0を返します。当初調査した[新しいAPIの公開契約](https://github.com/sahlberg/libnfs/blob/affe4c88829cd07bba082fe544df05d89c770d49/include/nfsc/libnfs-raw.h)では`*_task()`が要求へのポインターを返すため、そのままではビルドできませんでした。`LIBNFS_API_V2`でAPIの世代を判定し、呼び出しを切り替えます。この定数はNFSプロトコルv2の意味ではありません。

高水準の読み取りAPIも、5.0.2ではコールバック中だけ有効な受信データを返します。新しいAPIで使う呼び出し側のバッファへ統一するため、その有効期間内にコピーする構成です。ポート設定は5.0.2の公開URL解析APIで指定し、名前のバイト列と設定値を分離します。非公開APIや外部コードの修正は不要です。

| 対象 | 実装方針 |
| --- | --- |
| NFS v3 | libnfsの高水準非同期APIを使う |
| NFS v4 | v4.0を必須の検証対象とする。v4.2を追加する場合は、システムライブラリの対応と実通信を確認する。未検証のminor versionまで一括して対応済みとしない |
| NFS v2 | RAW RPCでmount、ファイルハンドル解決、列挙、属性、送受信、変更操作を組み立てる |
| 非同期実行 | ソケットのreadinessとRPCの期限をCardioに接続する。libnfsの同期APIや内部ワーカースレッドを通常の実行経路にしない |

## exportsとNFS v4の公開ツリー

NFS v2・v3のexports列挙に使うのはMOUNTプロトコルです。v2にはMOUNT v1、v3には対応するMOUNTの版を使い、汎用の列挙関数が使える組合せをドライバーで確認します。一覧取得の失敗と、既知のexportへ接続できないことを同じ扱いにしません。

NFS v4はMOUNTの機能をNFS本体に統合しており、v4専用サーバーにMOUNTによる完全なexports一覧を要求できません。公開名前空間のルートから探索する方式と、既知の公開パスを登録する方式を用意します。根拠は[RFC 7530の7節](https://www.rfc-editor.org/rfc/rfc7530.html#section-7)です。

| サーバーの応答 | アプリ側のルート |
| --- | --- |
| v2・v3でexportsを列挙できる | 各exportをルート直下に表示する |
| 列挙を拒否するが既知のexportへ接続できる | 設定に登録した公開パスをルート直下に表示し、列挙失敗の理由を示す |
| v4専用で公開名前空間を閲覧できる | アクセス可能な公開パスを候補として表示する。サーバーのexport設定を完全取得したとは表示しない |
| v4の公開ツリーが深い、または途中を一覧できない | 明示されたv4の公開パスを入口として追加する |

v4の名前空間上のパスと、v3のexportパスは別の値として保持します。たとえばv3の`/srv/public`がv4では`/public`になる構成を、同じ文字列と推定して接続しません。v4の公開ツリーの通常ディレクトリも、明示的に入口として選んだ場合は公開ルートとして表示できます。

画面の`/`はサーバーの一覧です。exportの表示名にはサーバー上の絶対パスを指定文字コードで表示したものを使い、操作用パスでは先頭要素を衝突しない識別子へ変換します。初期案はexportの元のバイト列全体を一つのパーセント表記の要素にする方式です。`/srv/public`なら`/%2Fsrv%2Fpublic/file.txt`、`/`なら`/%2F/file.txt`とし、表示名と操作用識別子を混同しません。この表記はアプリ内部用で、libnfsへ渡す前に元のexportパスへ戻します。

同じbasename、入れ子のexports、空白、日本語、`%`を含む名前を区別します。サーバールートとexportそのものの削除・名前変更は禁止し、export内部だけを変更可能にします。別exportへの名前変更は拒否し、コピーによる移動へ自動変換しません。plan15のNFS公開ルートアイコンを適用します。

## ディレクトリ・ファイル名の文字コード

### 設定の範囲

NFS接続へ「ファイル名の文字コード」を追加します。設定キーの案は`[nfs] filename_encoding`、既定値は`UTF-8`です。`CP932`、`SHIFT-JIS`、`EUC-JP`など、実行環境で利用できる文字コードを選べるようにします。CP932とShift_JISは同一視せず、指定した変換を使います。

これはディレクトリ・ファイル名、公開パス、新しいリンク先の名前を解釈する設定です。端末通信の`[terminal] encoding`やファイル本文の文字コードとは独立させ、転送する本文のバイト列は変更しません。2026年11月2日の利用者の指定により、今回の対象はグローバル既定値と接続ごとの上書きです。テーマからの継承はplan23で実装します。どの設定層にも指定がない場合は、OSのロケールによらずUTF-8を使います。

指定の単位は接続で、一つの接続内のexportsへ共通に適用する構成です。異なる文字コードのexportは別の接続設定で扱えます。exportごとの上書きは将来の拡張候補とし、最初の実装に必須とはしません。名前ごとの自動推定や、UTF-8として読めたかどうかによる無断の切替は行いません。

NFS v2/v3はファイル名から文字コードを取得できず、同じディレクトリに異なる符号化の名前が混在することもあります。NFS v4もUTF-8を既定としますが、非UTF-8名を受け付けるサーバーへの明示設定を認めます。サーバーが拒否した名前を別の文字コードで再送しません。v4の根拠は[RFC 7530の12.4・12.8節](https://www.rfc-editor.org/rfc/rfc7530.html#section-12.4)です。サーバーのUTF-8対応情報だけからCP932などを特定することもできません。

文字コードは接続作成時に確定し、実行中の接続では変更不可とします。設定を変えて再接続した後に一覧を取得し直します。進行中のジョブ、待機中の要求、既存の識別子へ途中から別の変換規則を適用しません。

### 元の名前と表示名を別に保持する

libnfsの列挙結果やRAW RPCで受け取った名前は、所有権のあるバイト列としてコピーします。GTKへ渡す表示名は、そのコピーを指定文字コードからUTF-8へ変換して作ります。表示や検索の都合で、通信に使う名前を置き換えないことが基本です。

| 操作 | 使用する名前 |
| --- | --- |
| 列挙、属性取得、OPEN、削除 | 列挙済みの項目は元の名前・パスを使う。表示文字列から再エンコードしない |
| 名前変更 | 変更元は元の識別子、変更先の新しい一要素だけをUTF-8から指定文字コードへ変換する |
| 新規作成・送信 | 選択済みの親は元の識別子を使い、新しい子の名前だけを変換する |
| 公開ルートへの接続 | 列挙したexportは元のパスを使う。利用者が入力した既知パスは要素ごとに変換する |
| 一覧の表示・ソート・検索 | UTF-8の表示名を使う。同じ表示名でも識別子が異なる項目は残す |
| 復号できない名前 | 元のバイト列を保持し、16進表記と変換できない旨を表示する。一件の変換失敗で一覧全体を失敗にしない |

Unicode正規化は、同じ文字を表す異なるUnicode列を一定の形式へ揃える処理です。例えば「が」一文字の合成形（NFC）と、「か」と濁点を組み合わせた分解形（NFD）は、見た目が同じでもバイト列が異なります。

既存名にはUnicode正規化、大小文字の統一、前後の空白除去を加えません。新規名も入力されたUnicode列を基本とし、独自のNFC正規化は追加しない方針です。表示上同じに見える名前や、同じUnicode文字へ復号される別のバイト列を、クライアント側で一つの項目へまとめません。

表示用の16進表記は実名への入力構文と区別します。変換できない項目でも、元の識別子で閲覧・受信・削除・名前変更できる構成にします。ただし、ローカル保存名を作れない場合や複数の項目が同じ保存名になる場合は、名前の明示指定またはスキップを必要とします。表示用の代替文字をそのまま保存名にしたり、無断で上書きしたりしません。

シンボリックリンクの保存された対象もバイト列として保持し、表示名と区別します。別の文字コードのファイルシステムへリンクを複製する場合は、対象パスの対応を検証します。変換できないリンクを成功扱いで別の対象へ向けず、ジョブの判断待ちまたは未転送の結果へ反映します。

### 変換する境界とパスの検証

[既存の文字コード検証](../../../shared/src/settings/terminal-settings.cpp)はiconvによる双方向の変換可否を確認しています。これを参考にファイル名用の変換部品を用意し、端末ストリーム用の状態を共有しません。公開APIの契約は[iconvの仕様](https://pubs.opengroup.org/onlinepubs/9799919799/functions/iconv.html)と使用環境のヘッダーコメントで確認します。

新しい名前の変換は厳密に行います。不正なUTF-8、表現できない文字、途中までしか変換できない入力、非可逆変換をエラーとし、`//IGNORE`や`//TRANSLIT`による削除・近似置換を許可しません。必要な逆変換も確認し、元のUnicode列と異なる名前になる場合は要求を送る前に止めます。文字コード名が利用可能であることと、その名前を無損失で表現できることを別々に検査します。

パスの区切りは名前の変換前に構造として扱います。各要素の変換後にもNUL、`/`、`.`、`..`、空名、プロトコルのバイト数上限を検査します。NFSでは`0x5c`をSMBのような区切りにしないため、CP932の複数バイト文字の途中に現れる値も保持します。UTF-16などNULを含む表現を、libnfsの通常のパス引数へそのまま渡すことはできません。

libnfsのパスAPIには、符号化済みの実際のバイト列を渡します。ホスト、export、ファイルパスを個別に指定し、これらをNFS URLの解析APIへ渡しません。共有議論で指摘されたURL解析順序は、[5.0.2の`nfs_parse_url()`](https://github.com/sahlberg/libnfs/blob/libnfs-5.0.2/lib/libnfs.c)でも、パーセント表記の復号後に`?`を解釈する順序でした。文字コード変換、アプリ内部の識別子表記、URLのパーセント表記を別の処理にし、`?`、`#`、`%`を含む実名を変えません。

5.0.2にはポートを指定する専用の公開関数がありません。この設定に限り、固定ASCII文字列と検証済みの数値から作ったURLを`nfs_parse_url_incomplete()`へ渡します。同時に入れ子のexportへの暗黙の接続を無効にします。実際のホストやパスを含めないため、名前のバイト列には影響しません。設定項目は[公式READMEのURL書式](https://github.com/sahlberg/libnfs/blob/libnfs-5.0.2/README)で確認済みです。

### 共通転送コードへの変更

現在の`RemoteFileAttributes`には`name`と`path`がありますが、[転送エンジン](../../../elder-terms-terminal/src/file-transfer/file-transfer-engine.cpp)の再帰探索と削除は、親パスと`child.name`から子パスを再構築しています。[転送画面](../../../elder-terms-terminal/src/file-transfer/file-transfer-window.cpp)も、名前とパスを文字列としてGTKのモデルに保存します。NFSクライアントの内部だけで変換しても、この経路に表示名が混ざると元のバイト列を失います。

取得済みの項目への操作は、クライアントが返す`child.path`などの識別子を引き継ぐ契約へ変更します。新規の子の識別子は、親の識別子とUTF-8の入力名をクライアントへ渡して生成します。表示名の連結、basenameの取り直し、入力欄に表示した文字列からの復元を操作対象の決定に使いません。

識別子は生バイト列をGTKのUTF-8表示欄へ流さず保持できる形にします。クライアント側の所有データとUI用の識別子を対応させ、表示が同じ項目、再読込、名前変更、切断後の古いノードを区別します。再接続を越えて古い接続の識別子を使わない寿命も明示します。

この変更はFTP/FTPS・SFTPにも関係するため、[plan15の転送方式別調査](plan15-transfer-jobs-and-tree-icons.md#ファイル名の文字コードに関する追加調査)と整合させます。NFSに必要な共通契約は本planで検証し、FTPなどの新しい設定の実装まで無条件に同じ段階へ含めません。

## NFS v2で補う機能

| 機能 | 補完内容と検証対象 |
| --- | --- |
| 接続と公開ルート | PORTMAP/RPCBIND、MOUNT v1、取得したルートハンドルの所有と解放 |
| パス解決 | LOOKUPを組み合わせた各要素の解決、GETATTR、存在しない項目、`..`でexportを越えない処理 |
| 一覧 | READDIRのcookieによるページ取得と、必要なGETATTRによる種別・サイズの補完 |
| 受信 | READのオフセットと分割転送、短い応答、EOF、ゼロバイト |
| 送信 | CREATEとWRITE、短い書き込み、エラー後の一時ファイル、完了後のRENAME |
| ディレクトリ・ファイル変更 | MKDIR、RMDIR、REMOVE、RENAMEを共通インターフェイスへ対応させる |
| リンク・属性 | READLINK、SYMLINK、SETATTR。共通エンジンと同じくシンボリックリンクを無条件に再帰追跡しない |
| エラー | RPCの失敗とNFSの応答エラーを分け、アクセス拒否、消失、容量不足、古いハンドルを区別する |

NFS v2のデータ量・オフセット・サイズの表現には制限があります。検査の根拠は[RFC 1094](https://www.rfc-editor.org/rfc/rfc1094.html)と採用するXDR定義です。要求を送る前に範囲を検査し、サーバー固有の上限も分けて検証します。32ビット値を狭い型へ丸めたり、サイズが大きいファイルを成功したように切り詰めたりしません。

v2のCREATEやRENAMEを、排他的作成・上書きなしの原子的操作と仮定しません。共通エンジンが求める一時ファイルの所有証明と照合し、能力フラグには実際に保証できるものだけを返します。不確実な一時ファイルを失敗後に無条件で削除しない契約です。

READDIRが同じcookieを返し続ける場合も検出します。再試行で変更操作を重複実行しないよう、通信終了後の状態が不確実な場合はその事実をジョブ結果へ残します。サーバー再起動後の古いハンドルは破棄し、再接続で公開ルートから取得し直します。

## 接続設定と寿命

設定候補は、ホスト、NFSの版、v2/v3のTCP・UDP、初期公開パス、追加の既知パス、ファイル名の文字コード、ローカルディレクトリ、UID、GID、補助グループ、接続・要求の期限です。初期の認証は数値IDを渡すAUTH_SYSとし、RPCSEC_GSSなどを対応済みとして表示しません。プロトコルの版を明示した接続では、別の版に自動変更しません。

v2/v3の標準構成ではサービスのポートを探索し、固定ポート指定が必要な構成も段階1で検証します。予約済み送信元ポートを要求するサーバーについては、権限とlibnfsの公開APIで成立する接続方法を確認します。管理者権限が必要な試験環境の準備は、その時点で必要な導入内容を示します。

v3/v4はexportごとのクライアントを遅延して作り、サーバー単位の窓口が列挙とパス解決を担当します。v2も同じ外部契約とし、内部実装の共通化は責任が一致する部分に留めます。切断時は開始済みのコールバックを回収してからRPCコンテキストを破棄します。

SSH proxyは今回の必須対応に含めません。NFSのポート探索やUDPを、現在のSMB向けTCP転送へそのまま接続できるとは見なしません。追加する場合は到達経路を検証した別段階を設けます。

## 段階1：採用APIと実通信の検証ドライバー

システム版libnfsの公開APIを確認し、各版を明示するドライバーを作ります。動作の確認対象は、v3・v4.0の一覧と1ファイル受信、v2のMOUNT・LOOKUP・READです。実際に使用したプロトコルの版も確認します。

表示名と操作対象の分離を共通転送の試験用クライアントで先にRED・GREEN確認します。UTF-8、CP932、EUC-JPの名前と復号不能な名前について、実通信のドライバーで列挙・表示・読み取りまで観測します。選択した項目へ送る名前が元のバイト列と一致することを検査し、表示名の一致だけを合格条件にしません。

v2対応サーバー、v3サーバー、MOUNTを提供しないv4専用サーバーを試験環境として確保します。新しいLinux環境でv2が無効な場合は、v2対応の隔離VMなどを用意します。v3の成功をv2の代用にしません。完了条件は、各版の実通信と非同期停止、元の名前での再アクセスを観測でき、採用版・API・試験環境が確定することです。

### 段階1の実施結果

作業ブランチは`feature/nfs-transfer`です。システム版libnfs 5.0.2を使い、`ldd`で`/lib/x86_64-linux-gnu/libnfs.so.14`へのリンクを確認しました。libnfsのサブモジュールと専用ビルド設定は削除済みです。独自ライブラリへのRPATHも残っていません。

実行経路は高水準の非同期APIとRAW RPC APIです。内部ワーカースレッドを起動せず、再接続を無効にしています。Cardioのソケット待機と要求全体の期限を組み合わせる構成です。5.0.2のRAW APIに公開タイムアウト設定がなくても、無応答の要求を停止できます。停止後はコンテキストを破棄してコールバックを回収します。

試験用サーバーには、Debian bullseyeのLinux 5.10.0-46-amd64を使います。`CONFIG_NFSD_V2=y`を確認したゲストをQEMUで起動し、ホストのNFSサービスや公開設定は変更しません。標準ポート111を使う試験は、Podmanの非特権ネットワーク名前空間内で実行します。VMはスナップショットで動かし、試験後に破棄します。

| 検証 | 確認した結果 |
| --- | --- |
| v2専用サーバー | MOUNT v1、exports列挙、cookie付きREADDIR、LOOKUP、3バイト単位のREADとEOFを実通信で確認 |
| v3専用サーバー | MOUNT v3、exports列挙、高水準APIによる一覧・OPEN・分割READ・CLOSEを確認 |
| v4.0専用サーバー | v2・v3・v4.1・v4.2を無効にし、MOUNTとPORTMAPの待ち受けを停止。公開パス`/public`から一覧・受信を確認 |
| 実際のプロトコル | TCP上のRPC要求を観測し、選択したNFS・MOUNTの版とv4のminor version 0を確認。ライブラリの診断用APIに依存しない |
| 名前のバイト列 | UTF-8、CP932、SHIFT-JIS、EUC-JP、不正バイトが混在する一覧で、元の名前から受信した内容を照合 |
| 名前の境界 | 空白、`?`、`#`、`%`、CP932の途中の`0x5c`、NFC/NFD、ゼロバイトのファイルを確認 |
| 接続先ポート | v2/v3でPORTMAP探索と固定ポートをそれぞれ確認 |
| 予約済み送信元ポート | 必須のexportに、ネットワーク名前空間内の権限で接続。`CAP_NET_BIND_SERVICE`を外すと拒否されることを確認 |
| 非同期停止 | 各版で要求が相手へ届いた後に中止・切断・無応答を注入。コールバック回収、コンテキスト解放、失敗理由を確認。ASan/UBSanでも成功 |
| 共通転送 | 表示名からパスを再構築すると再帰受信・削除が失敗するREDを確認。取得済みの`child.path`を引き継ぐ修正後、既存の転送エンジン試験も成功 |

名前の変換部品は、iconvで指定した変換と逆変換を検証します。新規名の不正なUTF-8、非可逆変換、NUL、区切り、`.`・`..`、長さ超過を拒否します。既存名の復号失敗はUTF-8の16進表示へ変え、操作用の元のバイト列は保持します。APIの契約は[GNU C Libraryの公式文書](https://sourceware.org/glibc/manual/latest/html_node/Generic-Conversion-Interface.html)と`/usr/include/iconv.h`で照合しました。

初期実装で提供する転送はTCPとし、NFS v4は4.0を対象にします。5.0.2の[公開ヘッダー](https://github.com/sahlberg/libnfs/blob/libnfs-5.0.2/include/nfsc/libnfs.h)にある高水準APIはv3とv4を選択する契約です。UDPやv4.2は今回の実装・検証の対象に含めません。

システム版への切り替えでは、まず既存コードのビルドがAPI差異で失敗することを確認しました。公開APIに合わせた修正後は`-Werror`でビルドでき、上記の実通信試験と各版の中止・切断・無応答試験が成功しています。依存ライブラリを独自ビルドしないため、そのビルド専用だった警告抑制も削除しました。

再現コマンドは`make -C elder-terms-terminal/tests/nfs deps test`です。`SANITIZE=1`を指定した試験も、システム版で成功しました。アプリ側のASan/UBSan検証を有効にし、実通信のログを`.build/nfs-evidence/`へ出力します。共通転送は段階1のコミット時点で、`meson compile -C .build sftp-transfer-engine-test`と`.build/elder-terms-terminal/sftp-transfer-engine-test`で確認済みです。全体の`make test`は段階6で実行します。

plan23のテーマ機能は現在のコードでは未実装です。利用者への確認により、今回の設定対象をグローバル既定値と接続設定に確定しました。テーマ連携はplan23で実装します。

## 段階2：NFS v3と公開ルートを画面で利用する

v3の一覧・送受信・変更操作を`RemoteFileClient`へ実装し、設定と転送画面へ組み込みます。公開ルートの衝突しないパス、変更禁止、既知パス、アクセス拒否から別exportへの移動を確認します。文字コードの保存・継承・再接続時の反映、非UTF-8名の表示、新規名の厳密変換、元の識別子を使った再帰転送・削除・名前変更を完成させます。

完了条件は、画面から複数exportを扱え、指定した文字コードでファイル・ディレクトリを双方向に転送して名前と内容を比較できることです。変換できない新規名ではリモートを変更しないことも確認します。ここで実際に使える一方式を完成させます。

## 段階3：NFS v4の公開ツリーと転送を統合する

v4.0の公開名前空間と登録パスをアプリ側のルートへ対応させます。MOUNTの有無にかかわらず接続できること、v3と異なるパス、権限拒否、サーバー再起動、状態を保持する接続の終了を検証します。

UTF-8を既定として、非UTF-8名を受け付けるサーバーと拒否するサーバーを区別します。明示設定で送信したバイト列、サーバーのエラー、正規化が異なる名前を検証し、別の文字コードへの自動再送を行わないことを確認します。

v4.2を提供する場合は、この段階で専用の設定値と実通信試験を追加します。完了条件は、保証するminor versionが明確で、v4専用サーバーを画面から閲覧・送受信できることです。

## 段階4：NFS v2の閲覧と受信を完成させる

RAW RPCの結果を所有権のある値へ変換し、パス解決、ページ付き一覧、属性、読み取りを実装します。名前の元のバイト列も保持し、v3と同じ表示・変換の規則へ接続します。画面へ読み取り専用として接続し、書き込み能力はこの段階では無効にします。

完了条件は、v2だけを提供するサーバーで深いディレクトリを閲覧・再帰受信でき、循環するリンク、READDIRの異常、短いREAD、サイズ上限を正しく扱うことです。

## 段階5：NFS v2の送信と変更操作を完成させる

送信、作成、削除、名前変更、リンクと属性を実装し、確認済みの能力を有効にします。各操作のRED・GREENを確認してから、同じGUIで実行できる状態へ進めます。

完了条件は、v2の双方向転送で内容が一致し、中止・切断・容量不足で成功を誤表示しないことです。exportルートと無関係なファイルを変更しないことも検証します。

## 段階6：版ごとの統合試験と全体検証

全版で複数export、入れ子の公開パス、日本語名、ゼロバイト、読み取り専用、認証ID、長い一覧、再接続、ウインドウ破棄を確認します。v2のTCP・UDPを提供する場合は両方を検証します。上限付近の転送は境界値テストと実通信試験を分けます。

文字コードについては次の条件を、サーバー上の名前のバイト列と内容で検証します。

| ケース | 確認する結果 |
| --- | --- |
| すべての設定層で文字コードを未指定 | OSのロケールや端末通信の設定によらずUTF-8を使う |
| UTF-8・CP932・Shift_JIS・EUC-JP | 正しく表示し、列挙後の受信・削除・名前変更で元の項目を操作する |
| 混在、不正バイト、同じ表示名になる別名 | 一覧と項目の識別を保ち、誤った項目へアクセスしない |
| NFC/NFD、空白、`?`、`#`、`%`、CP932の途中の`0x5c` | 元の名前を正規化・URL解析・区切り置換で変えない |
| 新規名の変換不能、NUL・区切りの生成、バイト数超過 | 送信前に失敗し、代替名で作成・上書きしない |
| ローカル保存名の衝突と復号不能 | 明示名またはスキップを使い、選択した元の項目とジョブ結果を保持する |
| 設定変更と再接続 | 古いジョブ・ノードを別の文字コードで再解釈せず、新しい接続から反映する |

共通パス処理の変更後はFTP/FTPS、SFTP、WebDAV、SMBの既存操作も回帰検証します。

plan15のジョブ結果、アイコン、進捗動画、利用者向け説明を確認し、`make test`を実行します。必要なv2・v4専用試験が未実施なら、その版の完了条件を満たしたとは記録しません。

## 最終完了条件

1. NFS v2・v3・v4.0を明示して接続し、各版で閲覧・送受信・必要な変更操作を実行できる。
2. exportsを衝突しないルート直下の擬似パスとして扱い、ルートそのものを変更できない。
3. v4専用サーバーと列挙拒否のサーバーで、公開ツリーまたは既知パスから操作できる。
4. v2の不足機能をアプリ側で補完し、サイズ制限、RPCの期限、切断、古いハンドルを扱える。
5. ファイル名の文字コードはUTF-8を既定とし、設定・継承・保存できる。既存名の元のバイト列と表示名を分離して、各版の操作で正しい項目を扱える。
6. 変換不能・混在・名前の衝突で項目を失わず、新規名の近似置換や無断の正規化を行わない。libnfsのパスAPIへ実際のバイト列を渡す。
7. 各版の実通信、共通転送の回帰、ジョブ・アイコン、全体テストが通り、外部ソースを変更していない。
