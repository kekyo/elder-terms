# SSH proxy対応計画

## 目的と調査状況

SSH踏み台を経由して最終接続先のTCPポートへ接続できるようにする。
SSH proxyを複数の接続タイプで共通に使う通信経路として扱い、設定UIを独立した「SSH proxy」タブへ集約する。

本書は2026年10月9日に行った現行コードの調査と設計案を保存した実装計画である。
保存時点のリビジョンは `5e39cac` で、機能の実装および踏み台経由の接続試験は未実施。
実現性はプロジェクトのコード、公式ドキュメント、公開APIのコメントから判断している。
調査環境のlibsshは0.10.6、libcurlは8.5.0である。これらは調査環境のバージョンであり、新しい最低要求バージョンの指定ではない。

## 接続タイプごとの実現性

| 接続タイプ | 実現性 | 対応方針 |
| --- | --- | --- |
| SSH | 対応可能 | 踏み台のTCP転送チャネルを通して、最終接続先とのSSH接続を確立する。踏み台と最終接続先は別々に認証する。 |
| SFTP | 対応可能 | SSHと同じ接続基盤を利用する。SFTP単独起動と、SSH端末から開くSFTPの両方を対象とする。 |
| Telnet | 対応可能 | TCP通信を転送チャネルに通し、既存のTelnetプロトコル処理を利用する。 |
| WebDAV（HTTP／HTTPS） | 対応可能 | libcurlの通信をSSHトンネルへ通す。HTTPSでは最終接続先とのTLSを維持する。 |
| FTP／FTPS・パッシブ | 対応可能 | 制御接続と、一覧取得・ファイル転送ごとのデータ接続をすべて踏み台へ通す。 |
| FTP／FTPS・アクティブ | 別設計が必要 | サーバーからの接続を受ける逆方向転送などが必要。今回の対応対象から除外する。 |
| ローカルシェル | 適用対象なし | ローカルプロセスの起動には適用しない。 |
| シリアル | 現在の方式には適用対象なし | ローカルのシリアルデバイスには適用しない。リモート機器を扱う場合は、別途ネットワーク経由の接続機能が必要。 |

SSHのTCP転送は、接続先のホスト名またはIPアドレスとポートを指定して利用できる。
libsshにはこのための公開API `ssh_channel_open_forward()` がある。
ただし、このAPIは転送チャネルの確立までを行い、ソケットとのデータ中継はアプリケーション側で実装する必要がある。
[RFC 4254のTCP転送仕様](https://www.rfc-editor.org/rfc/rfc4254.html#section-7.2)、[libsshの転送API](https://api.libssh.org/stable/group__libssh__channel.html)、[libsshの転送チュートリアル](https://api.libssh.org/stable/libssh_tutor_forwarding.html)を参照。

libcurlの通常のプロキシ設定ではアクティブFTPを利用できない。
SSH proxyが有効なFTP／FTPS接続では、アクティブモードとの組み合わせを設定検証で拒否する。
自動的にパッシブモードへ変更せず、利用者に変更を求める。
[libcurlのプロキシ仕様](https://curl.se/libcurl/c/CURLOPT_PROXY.html)を参照。

## 設定とUI

### 設定項目

独立した `[ssh_proxy]` セクションに保存する。キー名と基本仕様は次の案とする。

| UI項目 | INIキー | 組み込み既定値 | 内容 |
| --- | --- | --- | --- |
| 利用設定 | `enabled` | `false` | 接続別UIでは「継承／使用しない／使用する」を選ぶ。 |
| サーバー | `address` | 空 | 踏み台のホスト名、IPv4またはIPv6アドレス。使用時に必須。 |
| ポート | `port` | `22` | 踏み台のTCPポート。1～65535。 |
| ユーザー名 | `username` | 空 | 踏み台のログイン名。空の場合の扱いは既存のSSH認証処理に合わせる。 |
| 秘密鍵 | `identity_file` | 空 | 踏み台の認証に使用する鍵。空の場合の扱いは既存のSSH認証処理に合わせる。 |

各項目は既存のグローバル設定・接続別設定の継承に合わせる。
「継承」は設定ストアの継承状態で表し、`enabled` に別の文字列値を追加しない。
接続別に `enabled=false` を指定すれば、グローバル設定で有効になっていても直接接続を選べる。

例えばSSH接続では、最終接続先と踏み台を次のように分けて保存する。

```ini
[general]
type=ssh

[ssh]
address=internal.example
port=22
username=target-user

[ssh_proxy]
enabled=true
address=bastion.example
port=22
username=jump-user
identity_file=/home/user/.ssh/bastion_key
```

型付き設定は、利用状態と `SshEndpointSettings` を組み合わせた共通設定として持つ。
最終接続先の `[ssh]` の値を踏み台へ暗黙に流用せず、両者に異なるユーザー名・秘密鍵を指定できるようにする。
パスワードと鍵のパスフレーズは接続時に既存のプロンプトで入力し、設定ファイルへ保存しない。
踏み台用の端末種別やPTY設定は追加しない。

### 表示と操作

- 独立した「SSH proxy」タブに項目を集約する。各プロトコルのタブには最終接続先の設定を置く。
- グローバル設定と、実装済みの対応接続タイプの設定画面に表示する。最終的な対象はSSH、SFTP、Telnet、FTP、WebDAV。
- ローカルシェルとシリアルではタブを非表示にし、グローバル設定から継承したproxyを適用しない。
- proxyを使用しない間も入力済みの踏み台情報を保持し、再度有効にしたときに利用できるようにする。
- 接続中の設定画面では、既存の接続先設定と同様に読み取り専用とする。変更は保存済み接続を編集して再接続したときに反映する。
- プロンプトには「踏み台への認証」「接続先への認証」の区別と対象ホストを表示する。ホスト鍵の確認でも対象を明示する。
- SSH proxyとアクティブFTP／FTPSの併用は設定検証で拒否し、パッシブモードの選択が必要であることを表示する。

### 検証

proxy使用時には、サーバーの未入力、無効なポート、利用設定の不正な値などを接続前に検出する。
継承元にある無効な値も対象にする。
無効な値を既定の `enabled=false` へ置き換えて直接接続することは認めない。
UIだけでなく、INIを直接編集して起動した場合にも同じ条件で拒否する。

段階的な実装の途中では、まだ対応していないネットワーク接続タイプにproxy有効設定が渡された場合も直接接続へ流さず、未対応として通知する。

## 通信経路の設計

### 共通のSSH転送基盤

接続経路は `elder-terms → SSH踏み台 → 最終接続先のTCPポート` とする。
最初の対応は踏み台1台に限定する。

既存のSSHトランスポートのホスト鍵検証、公開鍵・パスワード・keyboard-interactive認証、ユーザー入力の処理を再利用する。
認証済みの踏み台接続上で、必要な宛先ごとにTCP転送チャネルを開く。
踏み台へ接続する処理自身には、同じproxy設定を再帰的に適用しない。

転送基盤は宛先ホスト名・ポートに対する通信と寿命管理を担当し、TelnetやHTTPなどのプロトコル処理は既存のバックエンドが担当する。
新しい構成要素は、インターフェイスの分離と移譲を優先する。

データ中継は `cardio` による非同期処理とする。
転送のための安易なワーカースレッド追加や時間間隔でのポーリングは行わず、既存SSHトランスポートの呼び出し直列化と整合させる。
双方向の部分読み書き、送受信速度の差による待機、バッファ上限、EOF、片方向の終了、キャンセル、切断を扱う。

### SSH／SFTP／Telnet向けの接続済みFD

転送チャネルとローカルの接続済みFDを双方向に中継するアダプターを用意する。
`socketpair` などの接続済みソケットで、既存バックエンドがFDとして読み書きできる構成を検討する。

SSHでは、このFDを使って最終接続先との独立したSSH接続を確立する。
最終接続先のホスト名・ポートは保持し、その相手のホスト鍵検証と認証を実施する。
SFTPは最終接続先の認証済みSSHトランスポート上で動作させる。
Telnetは取得したFD上で既存のネゴシエーションと送受信を行う。

FDだけを返して転送処理の所有者が失われる構成を避け、接続の所有オブジェクトが中継処理と踏み台接続を保持する。
libssh 0.10以降では `SSH_OPTIONS_FD` で渡したソケットのクローズは呼び出し側の責任となるため、成功・失敗・キャンセルのすべてで所有権を明確にする。
[libsshのFD所有権](https://api.libssh.org/stable/group__libssh__session.html)を参照。

### libcurl向けのSOCKS5アダプター

アプリケーション内で寿命を管理するSOCKS5アダプターを同じSSH転送基盤の上に設ける。
libcurlからの接続要求を宛先ごとのSSH転送チャネルへ対応させる。
接続口の具体的な方式と保護は実装時に確定し、外部ネットワークに汎用proxyとして公開しない。

libcurlには `socks5h` を指定し、宛先の名前解決を踏み台側へ委ねる。
SSHサーバーへSOCKSの要求を直接送る構成ではなく、アダプターがSOCKSの接続要求をSSHのTCP転送へ変換する。
WebDAVとFTP／FTPSでこの仕組みを共用する。
[libcurlのSOCKSと名前解決](https://curl.se/libcurl/c/CURLOPT_PROXY.html)を参照。

WebDAVでは新しく開く各HTTP接続を転送する。
FTP／FTPSでは制御接続だけでなく、動的に決まるパッシブデータポートへの接続も転送する。
制御ポートだけを固定転送する方式では、一覧取得やファイル転送を満たせない。

URLは最終接続先のものを保ち、HTTPのHost、TLSのSNI、証明書検証の対象がローカルの中継先へ置き換わらないようにする。
既存の証明書エラー確認や、変更操作を自動再送しない方針を維持する。

## 名前解決、検証、失敗時の動作

- 踏み台の名前はクライアント側で解決する。最終接続先の名前はSSH転送の宛先として渡し、踏み台側で解決する。手元では解決できない内部DNS名を扱えることを確認する。
- 踏み台と最終接続先のSSHホスト鍵をそれぞれ検証する。最終接続先の鍵を中継用のlocalhostや一時ポートの鍵として登録しない。
- HTTPS／FTPSでは本来の最終接続先名を用いてTLS証明書を検証する。SSHトンネルの存在を理由に検証を省略しない。
- proxy接続の失敗、認証拒否、TCP転送拒否、設定不備があっても直接接続へ切り替えない。
- libcurlでは `CURLOPT_NOPROXY` に空文字列を設定し、環境変数 `NO_PROXY` や `no_proxy` がproxyを迂回させないようにする。[公式仕様](https://curl.se/libcurl/c/CURLOPT_NOPROXY.html)を参照。
- 認証・確認のキャンセルとウィンドウの終了を、進行中の接続・転送へ伝える。踏み台への接続失敗と最終接続先への接続失敗を区別できる情報を表示する。
- 再接続では有効な設定から新しい経路を構築し、以前の中継処理や接続を残さない。

踏み台側にはTCP転送の許可が必要である。
OpenSSHでは `AllowTcpForwarding`、`PermitOpen` などの設定や認証鍵ごとの制限によって拒否される場合がある。
[OpenSSHのサーバー設定](https://man.openbsd.org/sshd_config)を参照。

Telnet、平文FTP、HTTPでは、踏み台から最終接続先までの区間は平文になる。
SSH proxyを利用することと、最終接続先までプロトコル自体が暗号化されることは区別して利用者向け文書に説明する。

## SFTP共有と終了処理

SSH端末から開くSFTPは、現在と同じく最終接続先の認証済みSSHトランスポートを共有する。
踏み台のSSH接続に対してSFTPを開始しない。

最終接続先のSSHトランスポートが、その通信経路と踏み台接続を保持する。
端末とSFTPの一方だけを閉じた場合も、他方が利用している接続を終了させない。
最後の所有者が解放されたときに、転送チャネル、中継処理、FD、踏み台接続を解放する。
接続失敗やキャンセルで途中まで生成されたリソースも対象とする。

SFTP単独起動とSFTPの再接続にも同じ経路構築を適用する。
独立した接続ウィンドウ間で踏み台接続を共有する接続プールは、今回の範囲には含めない。

## 段階的な実装

各段階を、ビルド可能で、アプリケーションから実装内容を観測できる単位で進める。
対象の振る舞いを検証するテストを先に追加してREDを確認し、実装後にGREENを確認する。
必要な確認を終えた単位で `feat:`、`fix:`、`refactor:`、`chore:`、`doc:` のいずれかを付けてコミットする。

大きな段階は「SSH／SFTP／Telnet」「WebDAV」「FTP／FTPS」の順とし、最初の段階をさらに実行可能な単位へ分割する。

### 段階1-1: 共通設定、タブ、転送基盤とTelnet

実装内容:

- `[ssh_proxy]` の設定定義、継承、保存・読み込み、検証を追加する。
- グローバル設定とTelnet設定にSSH proxyタブを追加し、既存のローカライズの仕組みに組み込む。
- 踏み台へのSSH接続・認証、TCP転送チャネル、接続済みFDへの中継を実装する。
- Telnetの接続経路選択と、踏み台用の認証・ホスト鍵プロンプトを接続する。
- 未対応のネットワーク接続タイプへproxy有効設定が渡された場合の拒否を実装する。

観測する成果物は、接続設定を保存し、UIから踏み台経由で接続できるTelnet端末とする。

完了条件:

- 設定の保存・再読み込みと、グローバル設定の継承・明示的な無効化が動作する。
- 踏み台側だけで解決できる宛先へ接続し、Telnetのネゴシエーションと双方向入出力が動作する。
- 認証拒否、転送拒否、不正設定、キャンセルで直接接続が発生しない。
- 切断・再接続・終了で中継処理とFDが解放され、直接接続の既存テストも成功する。
- アプリケーションをビルドでき、関連する設定・UI・Telnet・転送基盤のテストが成功する。

### 段階1-2: SSH端末

実装内容:

- SSH接続に共通の経路設定を渡し、直接接続と踏み台経由を選択する。
- 転送されたFD上で最終接続先のSSH接続を確立する。
- 踏み台と最終接続先のホスト鍵検証・認証を分離し、UIに対象を表示する。
- SSH設定にSSH proxyタブを表示する。

観測する成果物は、踏み台と最終接続先に別の認証情報を設定して利用できるSSH端末とする。

完了条件:

- 異なるユーザー名・秘密鍵を使う二段階の認証で、最終接続先のシェルを利用できる。
- 双方の未知のホスト鍵・変更されたホスト鍵と、最終接続先の接続失敗を正しい対象として扱える。
- 最終接続先のホスト名・ポートに対応するknown_hosts検証が動作する。
- 入出力、端末サイズ変更、切断・キャンセル・再接続が動作する。
- アプリケーションのビルドと関連するSSH・設定UIのテストが成功する。

### 段階1-3: SFTP単独起動とSSH端末との共有

実装内容:

- SFTP単独起動・再接続にproxy設定を渡し、SFTP設定にもタブを表示する。
- SSH端末から開くSFTPで、最終接続先のトランスポートとトンネルの共有を確認・調整する。
- 端末、SFTP、中継処理、踏み台接続の寿命を整合させる。

観測する成果物は、単独起動でもSSH端末からの起動でも利用できるSFTPウィンドウとする。

完了条件:

- 両方の起動方法で一覧取得、アップロード、ダウンロードが最終接続先に対して動作する。
- SSH端末から開いたSFTPは認証済みの接続を共有し、不要な再認証を要求しない。
- 端末とSFTPの一方を閉じても他方を利用でき、両方の終了後に接続とFDが残らない。
- 転送中断、踏み台切断、再接続を扱え、関連するSFTP・接続寿命のテストが成功する。
- 段階1全体として、SSH／SFTP／Telnetを同じ設定モデルと転送基盤で利用できる。

### 段階2: SOCKS5アダプターとWebDAV

実装内容:

- SSH転送基盤にlibcurl用のSOCKS5アダプターを追加する。
- WebDAVの起動・再接続とHTTPセッションへ経路を渡す。
- `socks5h` と `CURLOPT_NOPROXY` を設定し、内部DNS名と迂回防止を扱う。
- WebDAV設定にSSH proxyタブを表示する。
- 利用者向けのWebDAV文書で、今回対応したproxyの範囲を説明する。

観測する成果物は、内部DNS名を使用したHTTP／HTTPSのWebDAV接続とする。

完了条件:

- 一覧取得、アップロード、ダウンロード、既存のファイル操作が踏み台経由で動作する。
- ローカルでは解決できない宛先名を使え、Host、SNI、証明書検証が最終接続先を対象とする。
- 証明書エラーの拒否・確認が既存方針に従い、変更操作を自動再送しない。
- `NO_PROXY`／`no_proxy` が宛先に一致していても直接接続が発生しない。
- キャンセル・切断・再接続時にSOCKS接続とSSH転送チャネルを解放する。
- ビルドと関連するWebDAV・TLS・UIのテストが成功する。

### 段階3: FTP／FTPSのパッシブ対応と全体検証

実装内容:

- FTP起動・再接続とlibcurlセッションに共通のSOCKS5アダプターを組み込む。
- 制御接続とパッシブデータ接続の両方を同じ踏み台へ通す。
- EPSVとIPv4でのPASVフォールバックを検証する。
- PASV応答中の別ホストアドレスを採用せず、最終接続先のホストを使用する既存方針を維持する。
- SSH proxyとアクティブFTP／FTPSの併用を、UIとINI経由の起動の両方で拒否する。
- FTP設定にSSH proxyタブを表示し、日英の関連文書の対応範囲・制約を更新する。
- 機能全体の回帰テストとリソース解放を確認する。

観測する成果物は、パッシブFTP、明示的FTPS、暗黙的FTPSを利用できるファイル転送ウィンドウとする。

完了条件:

- 一覧取得、アップロード、ダウンロードで、制御接続と各データ接続が踏み台を通る。
- EPSVとPASVの両方で動作し、データ接続が直接接続や別ホストへの接続にならない。
- 明示的／暗黙的FTPSで制御・データ接続のTLSと既存の証明書検証が動作する。
- 既存のTLSセッション再利用要件や接続再作成の方針と両立する。
- アクティブとの併用を接続前に拒否し、設定値を黙って変更しない。
- 関連テストに加え、プロジェクトの全体テストが成功する。

## テスト方針

既存のC++テスト、Vitest、GTKのテスト基盤を利用する。
主な参照先は [設定テスト](../../../shared/tests/settings-test.cpp)、[設定UIテスト](../../../shared/tests/settings-widget.test.ts)、[SSH接続テスト](../../../elder-terms-vte/tests/cpp/ssh-channel-connection-test.cpp)、[Telnetテスト](../../../elder-terms-vte/tests/telnet-session.test.ts)、[SFTP UIテスト](../../../elder-terms-vte/tests/sftp-window.test.ts)、[WebDAVテスト](../../../elder-terms-vte/tests/cpp/webdav-client-test.cpp)、[FTPテスト](../../../elder-terms-vte/tests/cpp/curl-ftp-client-test.cpp)とする。

テストでは、設定ファイルやソースに特定の文字列が存在することではなく、公開された設定操作と実際の通信結果を検証する。
踏み台と最終接続先を別のテストサーバーとして用意し、接続要求・認証対象・受信データを確認する。
宛先がローカルで到達可能なだけで成功しないよう、踏み台側だけで解決できる名前や、サーバー側の接続記録で経路を検証する。

| 観点 | 主な検証内容 |
| --- | --- |
| 設定 | 組み込み既定値、保存・再読み込み、継承、接続別の無効化、不正な値、無効な継承値。 |
| UI | 接続タイプ別のタブ表示、継承操作、接続中の読み取り専用、踏み台と接続先のプロンプトの区別。 |
| 接続経路 | 宛先名・ポートの伝達、踏み台側のDNS、IPv4／IPv6、proxy障害時と環境変数による直接接続の防止。 |
| SSH認証 | 踏み台と最終接続先の別認証、公開鍵・パスワード・keyboard-interactive、パスフレーズ、拒否・キャンセル。 |
| ホスト鍵・TLS | 踏み台と接続先の鍵の区別、鍵変更、正しい宛先名でのTLS検証、証明書エラーの既存方針。 |
| データ中継 | 部分読み書き、双方向通信、送受信速度の差、EOF、切断、キャンセル時に処理が終了すること。 |
| SFTP | 単独起動、端末との共有、双方の終了順序、転送中断、再接続。 |
| WebDAV | 一覧・ファイル操作、新しいHTTP接続、TLS、変更操作の自動再送が発生しないこと。 |
| FTP／FTPS | 制御・データ双方の経路、EPSV／PASV、明示的／暗黙的TLS、アクティブ併用の拒否。 |
| 寿命 | 接続失敗・認証中断・繰り返し再接続・ウィンドウ終了後にFDや中継処理が残らないこと。 |
| 回帰 | proxy無効時の直接接続、ローカルシェル、シリアル、既存のファイル操作。 |

非同期のテストはイベントや明示的な完了通知で同期し、固定時間のsleepによる成功判定を避ける。
必要なパッケージが不足する場合は、インストールを促し、未実行の検証を成功として扱わない。
UIの画像マスターを追加・変更する場合は目視確認し、時間軸の挙動を検証する必要が生じた場合は動画による確認を含める。

実装全体の完了時には、所要時間にかかわらずルートで `npm test` を実行する。
既存の `make test` は `npm test --workspaces` を起動する入口として利用できる。
段階ごとの関連テストだけで機能全体を完了扱いにしない。

## 対象外と実装時の確認事項

今回の対応範囲に含めないもの:

- 複数の踏み台を順に通る多段接続。
- SSH proxy利用時のアクティブFTP／FTPS。
- 任意のProxyCommand実行や、OpenSSHのProxyJump設定全般の互換実装。
- リモートシリアル接続、ローカルシェルのリモート実行化。
- 外部利用者向けの汎用SOCKSサービスや、独立した接続ウィンドウ間の踏み台接続プール。

実装時には、接続済みFDへの中継方式、SOCKS接続口の方式、既存トランスポートの呼び出し直列化との統合を確認する。
これらは本書の通信経路・認証・寿命の要件を満たす内部設計として決定する。
既存の外部ライブラリは公式ドキュメントと使用する版のAPIコメントを確認し、非推奨・内部APIを使用しない。サブモジュールやベンダーコードは変更しない。

実装やテストで前提と矛盾する結果が出た場合は、場当たり的に回避せず、本計画の設計と段階分けを再検討する。
対応範囲や期待する振る舞いを変える必要がある場合は、その相違を確認してから計画を更新する。
